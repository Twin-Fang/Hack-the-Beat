# 제출 가이드 — 심사 제출 페이지 실물 기준

> 출처: https://web-three-steel-62.vercel.app/submit (로그인 후 화면, 2026-08-29 14:35 저장본)
> 채점 기준: [judging-criteria.md](./judging-criteria.md) — 제출물은 전부 이 기준으로 읽힌다
> 팀 코드(운영진 발급 6자리)는 **이 문서·레포 어디에도 적지 않는다.**

## 0. 제출 전 반드시

| 항목 | 내용 |
|---|---|
| **1회성** | "제출하면 수정할 수 없습니다". 확인 체크박스(필수) + 버튼 이름이 **"제출하고 심사 시작"** → 누르는 순간 끝 |
| 누가 누르나 | 팀원 전원이 3절 체크리스트를 같이 보고 확인한 뒤 **한 명만** 누른다 |
| 로그인 | `/login` 에서 체크인 시 발급받은 **6자리 팀 코드** 입력 |
| 팀 이름 | 팀 코드가 아니라 **팀명**. 제출과 함께 확정, 변경 불가 |
| 심사 시작 | 버튼은 "제출하고 심사 시작"이지만 운영 설명상 **마감 후 일괄 실행**. 어느 쪽이든 제출 시점에 앱·문서가 완결돼 있어야 함 |
| 배포 프리즈 | 제출 후 서비스 URL·배포 내용을 바꾸지 않는다 (심사 시점에 열리는 화면이 채점 대상) |

→ 심사 에이전트에게 들어가는 것: **URL(+계정) · 3단계 · 기획안 · 스크립트 · (발표자료 텍스트)**. 이 다섯이 창업가·엔지니어·투자자 페르소나가 보는 전부다.

## 2. 필드별 작성 가이드

### ① 팀 이름
- 팀명 그대로. 리포트에 표시되므로 오타 확인.

### ② 서비스 URL
- 배포 주소 그대로: `https://twin-fang.github.io/Hack-the-Beat/` (끝 슬래시 포함)
- 제출 직전 **시크릿 창**에서 열어 첫 화면·3단계를 손으로 한 번 완주
- 첫 화면이 곧 1단계 시작점이어야 한다 (에이전트는 URL에서 출발)

### ③ ④ 테스트 계정
- **원칙: 비워둔다.** 핵심 플로우를 로그인 없이 완주 가능하게 만든다 (A1 실패 요인 하나 제거)
- 부득이 로그인이 있으면: 아이디·비밀번호를 넣고, 앱의 로그인 폼은 라벨 "아이디"/"비밀번호" + 버튼 "로그인"의 표준 형태로 (에이전트가 폼을 찾아야 함)
- 현재 스캐폴드의 `RequireAuth` 가드(`/` → `/login` 리다이렉트)는 **실제 제품에서 제거**하거나 첫 화면을 로그인 없는 페이지로 바꾼다

### ⑤ 핵심 플로우 3단계
- 한 줄에 **동작 하나 + 화면 텍스트 인용 + 성공 판정**. 에이전트가 이 문장을 그대로 실행한다
- 형식은 placeholder를 따른다: `N단계 — <동작>`
- 1단계는 첫 화면에서 바로 가능한 동작, 3단계 끝에 **완료 텍스트**가 화면에 보여야 함
- 2~3단계에 **초대/공유/동반 참여** 동작을 넣어 B3(파티형 확산 구조, 실효 9.9%) 검증을 같이 받는다
- 화면의 버튼·라벨과 **글자 단위로 동일**하게 쓴다 (예: 버튼이 "파티 만들기"면 "파티 생성"이라 쓰지 않는다)

예시:
```
1단계 — 첫 화면에서 "파티 만들기" 버튼을 누르고 "파티 이름"에 "생일파티"를 입력한 뒤 "만들기"를 누른다. 화면에 "파티가 만들어졌어요"가 보이면 성공
2단계 — "초대 링크 복사" 버튼을 누른다. "링크가 복사되었어요"가 보이고 화면에 초대 링크(URL)가 표시되면 성공
3단계 — 표시된 초대 링크로 접속해 "참여하기"를 누른다. "참여 완료"와 참여자 목록에 이름이 보이면 성공
```

### ⑥ 기획안 (markdown, 8,000자)
- 루브릭 항목 이름을 **소제목으로 그대로** 쓴다 → 페르소나가 항목별로 바로 찾는다
- **구현한 기능만** 쓴다 (미구현 기능 근거 = 6점 상한, 검증 실패 기능 근거 = 4점 상한)
- 숫자·고유명사·관찰만. "~할 계획/예정"(의도) 문장은 5점 상한
- 분량 가점 없음. 짧고 근거 밀도 높게

글자 예산 (8,000자 기준):

| 섹션 | 예산 | 채점 항목 |
|---|---|---|
| 한 줄 요약 + 주제 연결 | 400 | D |
| 타깃 고객 (누가·어떤 순간·왜 + 관찰/대화 인용) | 1,000 | B1 |
| 문제 → 솔루션 → 핵심 플로우 3단계 (구현된 화면 기준) | 1,500 | A3 |
| GTM — B2 최초 유입 채널 / B3 파티형 확산 구조 / B4 리텐션 트리거 | 2,000 | B2~B4 |
| 비즈니스 — C1 수익 모델 / C2 시장 규모(상향식) / C3 대체재·차별점 / C4 단위 경제성 | 2,400 | C1~C4 |
| 여유 | 700 | — |

### ⑦ 발표 스크립트 (markdown, 4,000자)
- **첫 문단에 주제 연결** ("파티 <전/중/후>의 <순간>에서 <불편>을 …")
- 기획안과 **같은 숫자·같은 기능명** (모순 나면 신뢰도 하락)
- 기획안의 B·C 근거를 압축 반복. 새 주장은 넣지 않는다
- 낭독용이 아니라 **심사용 텍스트**다. 인사말·감사 인사 빼고 근거로 채운다

### ⑧ 발표자료 (선택)
- 텍스트만 추출되고 **이미지 속 글씨는 못 읽음** → 숫자·핵심 문장은 반드시 텍스트 노드로
- 기획안·스크립트와 내용이 다르면 오히려 감점 위험. 시간 없으면 **생략**이 안전
- 넣는다면 HTML 슬라이드(텍스트 기반). 이미지 캡처 위주 슬라이드는 의미 없음

## 3. 제출 직전 체크리스트

- [ ] 시크릿 창에서 서비스 URL 열림, **콘솔 에러 0** (데스크톱 + 모바일 뷰포트)
- [ ] 3단계를 **문장 그대로** 손으로 따라 해 완주됨 (버튼 텍스트 글자 단위 일치)
- [ ] 3단계 안에 초대/공유/동반 참여 동작 포함
- [ ] 로그인 없이 1단계 시작 가능 (테스트 계정 비움) — 또는 계정 입력 + 표준 로그인 폼
- [ ] 기획안 ≤ 8,000자, 스크립트 ≤ 4,000자, 둘 다 markdown
- [ ] 기획안·스크립트의 기능 = 배포된 앱에서 실제 동작하는 기능
- [ ] 항목별 상한 해제 조건 충족 (B1 관찰 인용, B2 모수·주체·시점 중 둘, B3 실동작, B4 트리거 시점, C1 주체·시점·금액, C2 상향식 계산, C3 대체재 이름, C4 건당 비용) — [judging-criteria.md 7절](./judging-criteria.md#7-문서기획안스크립트발표자료-작성-규칙--bc-상한-해제-체크리스트)
- [ ] 첫 문단 주제 연결 (게이트 8점 이상)
- [ ] 팀 이름 오타 확인
- [ ] 제출 후 배포 프리즈 — main push 금지

## 4. 템플릿

### 3단계
```
1단계 — 첫 화면에서 "<버튼>" 버튼을 누르고 "<입력 라벨>"에 "<예시 값>"을 입력한 뒤 "<버튼>"을 누른다. "<완료 텍스트>"가 보이면 성공
2단계 — "<초대/공유 버튼>" 버튼을 누른다. "<완료 텍스트>"와 <초대 링크/코드>가 화면에 보이면 성공
3단계 — <초대 링크로 접속 / 코드 입력>해 "<참여 버튼>"을 누른다. "<완료 텍스트>"와 <참여자 목록/결과>가 보이면 성공
```

### 기획안 (markdown)
```markdown
# <서비스 이름> — <한 줄 요약>

## 주제 연결
파티 <전/중/후>의 <순간>에 <누가> 겪는 <불편>을 <어떻게> 해결한다. <초대/동반 참여> 없이는 동작하지 않는 구조.

## 타깃 고객
- 누가: <고유명사 수준 세그먼트>
- 어떤 순간: <상황>
- 왜: <불편>
- 관찰: <누구에게 물었는지 · 무엇을 봤는지 — 날짜·인원·인용문>

## 문제와 솔루션
- 문제: …
- 솔루션: …

## 핵심 플로우 (구현 완료)
1. <화면 텍스트 인용> …
2. …
3. …

## GTM 전략
### 최초 유입 채널의 현실성
- 채널: <커뮤니티 고유명사> (접근 가능 모수 <N>명)
- 실행 주체: <팀원 이름/역할>, 시점: <날짜>
- 왜 거기서 되는가: …
### 파티형 확산 구조
- 초대 링크 → 참여 → <동반 참여 동작>. 초대 없이는 <무엇>이 성립하지 않음 (3단계에서 검증)
### 리텐션 트리거
- 트리거: <무엇>이 <언제>(<조건>) 사용자를 다시 부름. 구현 위치: <화면>

## 비즈니스 가능성
### 수익 모델과 지불 의사
- 지불 주체 <누구> · 지불 시점 <언제> · 금액 <얼마> · 근거 <왜 그 가격>
### 시장 규모와 성장 논리
- 상향식: <대상 수> × <연 빈도> × <단가> = <금액>. 가정: …
### 방어 가능성·차별점
- 대체재: <카카오톡 단톡방 / 인스타그램 / …>가 못 하는 것: …
- 우리가 이기는 이유: …
### 단위 경제성·운영 확장성
- 건당 비용 <N원> (<내역>), 운영 인력 <N>명. 확장 경로: …
```

### 발표 스크립트 (markdown)
```markdown
# <서비스 이름>

<첫 문단: 주제 연결 — 파티 <순간>의 <불편>, 그걸 <초대/동반 참여> 구조로 푼다>

## 누가 왜 쓰나
<B1 근거 압축 — 관찰 인용 1개>

## 어떻게 동작하나
<3단계 그대로>

## 어떻게 퍼지나
<B2 채널·모수·주체·시점 / B3 초대 없으면 안 되는 이유 / B4 재방문 트리거>

## 어떻게 돈이 되나
<C1 주체·시점·금액 / C2 상향식 한 줄 / C3 대체재 이름 + 못 하는 점 / C4 건당 비용>
```

## 5. 자주 묻는 것

| 질문 | 답 |
|---|---|
| 테스트 계정 비워도 되나 | 로그인 없는 서비스면 비움. 비우면 에이전트는 로그인 시도 안 함 |
| 발표자료 꼭 내야 하나 | 선택. 텍스트만 읽히므로 이미지 슬라이드는 무의미. 시간 없으면 생략 |
| 글자 제한 | 기획안 8,000 / 스크립트 4,000 / 발표자료 400,000 |
| 제출 후 수정 | 불가. 팀 이름·URL 포함 전부 |
| 제출 후 앱 수정 | 하지 않는다 (배포 프리즈). 심사 시점 화면이 채점 대상 |
| 3단계 형식 | 한 줄씩, 화면 텍스트 인용, 에이전트가 순서대로 실행 |
| 어떤 자료가 페르소나에게 가나 | URL(+계정)·3단계·기획안·스크립트·발표자료 텍스트. 그 외는 없음 |
