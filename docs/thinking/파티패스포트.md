# 제안 — 파티 패스포트 (QR 태그 수집 · 증표 · 파티 후 상호 선택)

> 제안. 피크민이 걸음 수라면 이건 **파티에서 말 건 사람 수**다.
> "증표 받으려면 3명은 만나야 해"가 낯선 사람에게 말 걸 핑계가 된다.

## 1. 한 줄 — 파티 "중"의 어색함, "후"의 흐지부지

**파티 참가자가 서로의 QR을 태그해 "만난 사람 수"를 쌓고, 기준 인원을 넘기면 증표를 받으며,
파티가 끝나면 만난 사람 중 다시 만나고 싶은 사람을 골라 서로 고른 쌍만 공개하는 웹.**

**현장 문제**: 축제·오프사이트·생일파티에서 아는 사람끼리만 논다. 처음 보는 사람에게 말 걸 계기가 없고, 파티가 끝나면 누구를 만났는지도 남지 않는다.

### 흐름 (전 · 중 · 후)

| 순간 | 동작 |
|---|---|
| 전 | 호스트 `파티 만들기` (이름·인원) → 초대 링크 |
| 중 | 참가자 링크로 참여 → 내 QR + 4자리 코드 → 대화한 사람 QR을 **폰 기본 카메라**로 찍으면(=URL 열기) 둘 다 +1 → `K/N-1명 만남` 진행률 → 증표 발급 → 미션 상대 찾기 |
| 후 | 호스트 `파티 종료`(또는 24시간 경과) → 만난 사람 중 `다시 만나고 싶은 사람` 체크 → `선택 제출` → **서로 선택된 사람만** 표시 → 증표함에 기록 → `다음 파티 만들기` |

### 증표 (발급 조건 고정 — "강제로 N명 이상")

| 증표 | 조건 |
|---|---|
| 첫 만남 | 1명 |
| 아이스브레이커 | 3명 |
| 파티 피플 | 참가자 절반 이상 |
| 파티 마스터 | 전원 |
| 미션 완료 | 지정된 미션 상대와 만남 |
| 재회 | 서로 선택된 사람 1명 이상 |

### 1:1 미션 (일대일 대응)
참가 순서로 원형 배치, **각자의 미션 상대 = 다음 참가자**(마지막 → 첫 번째). 모두가 정확히 한 명의 상대이자 한 명의 타깃. 친한 사람끼리만 찍는 걸 막는 장치. 저장 없이 참가자 목록에서 계산.

## 2. 초대/동반 참여 없이는 안 되는 이유 (B3)

남의 QR을 찍어야 숫자가 오른다. 혼자면 0, 증표 0. **전원이 동시에 각자** 진행한다(릴레이처럼 한 번에 한 명만 활동하는 구조가 아님). 3단계 시나리오의 2~3단계(초대 링크 복사 → 접속·참여)가 그대로 B3 실동작 검증.

## 3. 단톡방·인스타·구글폼으로 안 되는 이유 (C3)

| 대체재 | 못 하는 지점 |
|---|---|
| 인스타 맞팔 | 파티 밖 관계까지 섞임. "이 파티에서" 만난 사람 수·진행률·증표·호스트 데이터 0 |
| 종이 스탬프 랠리 | 부스용이지 **사람용**이 아님. 사람마다 도장을 들고 다닐 수 없음 |
| Whova·Brella (컨퍼런스 앱) | 계정·수백만 원·사전 세팅. 파티 현장에서 즉석 생성 불가 |
| 단톡방·구글폼 | 상호 선택을 **비밀로** 계산 못 함. 사람이 개입하는 순간 누가 누굴 골랐는지 새어 나감 |

## 4. 다시 올 이유 (B4)

- 증표는 파티가 끝나도 **증표함에 남고 다음 파티에서 누적** (포켓몬고 메달 구조)
- **파티 종료 직후** 상호 선택 결과 공개 — 트리거 시점이 제품 동작으로 특정됨
- 결과 화면에 `다음 파티 만들기`

## 5. 제출 3단계 시나리오 초안 (submission-guide 형식)

```
1단계 — 첫 화면에서 "파티 만들기" 버튼을 누르고 "파티 이름"에 "금요일 파티"를 입력한 뒤 "파티 만들기"를 누른다. "초대 링크가 생성되었습니다"가 보이고 주소가 /party/로 바뀌면 성공
2단계 — "초대 링크 복사" 버튼을 누른다. "복사되었습니다"가 보이고 화면에 초대 링크(URL)가 표시되면 성공
3단계 — 표시된 초대 링크로 접속해 "이름"에 "김서준"을 입력하고 "참여하기"를 누른다. "참여 완료"와 참가자 목록에 "김서준"이 보이면 성공
```

**태그·종료·선택 화면은 시나리오에 넣지 않는다.** 단계가 무거워질수록 실패 확률만 오른다.
단, 심사 에이전트가 A3(기획안 대비 구현)를 확인할 수 있게 태그는 **URL 접속·`코드로 태그` 4자리 입력**으로도 동작한다 — Playwright는 카메라로 QR을 못 찍는다.

### 화면 텍스트 (글자 단위 고정)
`파티 만들기` · `파티 이름` · `초대 링크가 생성되었습니다` · `초대 링크 복사` · `복사되었습니다` · `이름` · `참여하기` · `참여 완료` · `코드로 태그` · `파티 종료` · `다시 만나고 싶은 사람` · `선택 제출` · `서로 선택된 사람` · `다음 파티 만들기` · `내 증표함`

## 6. 남은 시간에 완주 가능한가

| 시각 | 마일스톤 |
|---|---|
| +0:45 | 1~3단계 동작 (생성 · 초대 링크 복사 · 참여 · 참가자 목록) — **A1은 여기서 끝남** |
| +1:15 | 태그(URL·코드) · QR · 진행률 · 증표 · 미션 상대 |
| +1:45 | 파티 종료 · 다시 만나고 싶은 사람 · 서로 선택된 사람 · 증표함 |
| +2:00 | 빈/에러 상태, 모바일 375px, 콘솔 에러 0 |
| +2:10 | Playwright로 배포 URL 3단계 검증 → 배포 프리즈 |

- 1~3단계는 PARTY MOOD와 **같은 코드**(생성·초대·참여). 차이는 그 뒤 화면뿐.
- QR = URL 한 줄 + `qrcode.react` 컴포넌트 하나. 인앱 스캐너 없음(폰 기본 카메라가 URL을 연다).
- 태그·증표·미션은 순수 함수(집합 연산) + Firestore 문서 3종. 실시간 소켓 없음, 3초 폴링.
- **시간이 밀리면 "파티 후"부터 자른다.** 태그·증표까지만으로도 B3·B4·D 성립. 문서에는 배포에서 동작 확인된 기능만 쓴다.

### 저장소
Firebase Firestore(무료, 스키마 없음) — 서로 다른 폰이 같은 참가자 목록·만남 기록을 봐야 하므로 필수. GitHub Pages는 정적. **PARTY MOOD도 동일하게 필요**(참가자 버튼 → 호스트 화면).

```
parties/{id}                    { name, size, createdAt, endedAt }
parties/{id}/participants/{pid} { name, code, joinedAt }
parties/{id}/meets/{a_b}        { a, b, at }        // a<b 정렬 → 무방향·중복 불가
parties/{id}/picks/{pid}        { picks: [pid], at }
```

| 항목 | 실효 | 점수 | 근거 |
|---|---|---|---|
| D 게이트 | ×1.00 | 8~10 | "이 파티에서 만난 사람"이 전제. 선택은 **QR로 실제 만난 사람에게만** → 데이팅 앱과 구조적으로 다름 |
| B3 확산 | 9.9% | 10 | 남의 QR 없이는 숫자 자체가 안 오름 |

| C1 수익 | 9.9% | 7 | 호스트가 · 파티 생성 시 · 20명 초과분 9,900원 (화면에 요금 한 줄) |
| C3 차별점 | 9.9% | 7~8 | 위 대체재 표 |
| A1 | 13.6% | 10 | 검증된 3단계(생성·초대·참여) 그대로 |

## PARTY MOOD(파티 감정 온도계)와 비교 — 의견

| 항목 | PARTY MOOD | 파티 패스포트 |
|---|---|---|
| D 게이트 | 10 — 진행 중에만 의미 | 8~10 — 상호 선택 문구를 "다시 만나고 싶은 사람"으로 고정해야 함 |
| A 완주 위험 | 낮음 (버튼 4개 + 카운터) | 중간 — 단 1~3단계는 동일, 추가 화면은 시나리오 밖 |
| B3 확산 | **7** — 1명이 눌러도 제품은 그대로 돌아감(5점 앵커 "초대 없어도 동작"). 분포는 여럿이 있어야 생기지만 동작 자체는 혼자서도 됨 | **10** — 혼자면 기능 자체가 0 |
| B4 리텐션 | 6 — 온도 그래프 리포트 (호스트만 볼 이유) | 8 — 증표 누적 + 결과 공개 |
| 참가자 쪽 사용 이유 | 약함 (문서에서 스스로 인정) | 강함 — 증표·미션·결과가 참가자 것 |
| C3 | 7~8 — "단톡방에 어색하다고 안 쓴다", 슬라이도 지목 | 7~8 — 인스타 맞팔·스탬프 랠리·Whova 지목 |
| 엔지니어 페르소나 리스크 | 익명 버튼 반복 클릭 방어 없음, 임계치 로직이 얕음 | 태그 자기 자신/중복 방어(정렬된 쌍 ID)로 해결 |

같은 3단계 코드 위에서 **B3·B4·참가자 동기**가 올라간다. 대신 D·A 리스크를 문구 고정과 "파티 후부터 자르기"로 관리한다.

## 절대 붙이지 말 것
프로필 / 사진 / 채팅 / 로그인 / 연락처 수집 / 실시간 소켓. 문서에서 "소개팅·호감·데이팅" 단어 금지 → "다시 만나고 싶은 사람".
