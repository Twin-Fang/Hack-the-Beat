# 제안 — 파티 패스포트 (QR 태그 수집 · 증표 · 파티 후 상호 선택)

> 제안. 피크민이 걸음 수라면 이건 **파티에서 말 건 사람 수**다.
> "증표 받으려면 3명은 만나야 해"가 낯선 사람에게 말 걸 핑계가 된다.

> **v2 — [personas](../personas/) 3종(창업가·엔지니어·투자자) 자가 심사 반영.**
> 바뀐 곳: ① 3단계 안에 태그·증표 진입(6점 상한 해제) ② 폴링 → `onSnapshot`(무료 티어 소진 방지)
> ③ 상호 선택을 Firestore 규칙으로 강제 ④ B1·B2·C2·C4 신설
> **자가 채점표는 넣지 않는다 — 별도 세션에서 페르소나 검증을 돌린다.**

## 1. 한 줄 — 파티 "중"의 어색함, "후"의 흐지부지

**파티 참가자가 서로의 QR을 태그해 "만난 사람 수"를 쌓고, 기준 인원을 넘기면 증표를 받으며,
파티가 끝나면 만난 사람 중 다시 만나고 싶은 사람을 골라 서로 고른 쌍만 공개하는 웹.**

**현장 문제**: 축제·오프사이트·생일파티에서 아는 사람끼리만 논다. 처음 보는 사람에게 말 걸 계기가 없고, 파티가 끝나면 누구를 만났는지도 남지 않는다.

### 흐름 (전 · 중 · 후)

| 순간 | 동작 |
|---|---|
| 전 | 호스트 `파티 만들기` (이름·인원) → 초대 링크 |
| 중 | **초대 링크로 참여하면 초대한 사람과 즉시 서로 +1** → 내 QR + 4자리 코드 → 대화한 사람 QR을 **폰 기본 카메라**로 찍으면(=URL 열기) 둘 다 +1 → `K/N-1명 만남` 진행률 → 증표 발급 → 미션 상대 찾기 |
| 후 | 호스트 `파티 종료`(또는 생성 24시간 경과) → 만난 사람 중 `다시 만나고 싶은 사람` 체크 → `선택 제출` → **서로 선택된 사람만** 표시 → 증표함에 기록 → `다음 파티 만들기` |

**초대 링크에 초대한 사람의 코드가 실린다** (`/party/<id>?from=<code>`). 링크를 준 사람은 실제로 만난 사람이므로 자동 태그가 논리적으로 성립하고, 3단계 시나리오 안에서 태그·증표가 evidence에 남는다.

### 증표 (발급 조건 고정 — "강제로 N명 이상")

| 증표 | 조건 |
|---|---|
| 첫 만남 | 1명 |
| 아이스브레이커 | 3명 |
| 파티 피플 | 참가자 절반 이상 |
| 파티 마스터 | 전원 |
| 미션 완료 | 지정된 미션 상대와 만남 |
| 재회 | 서로 선택된 사람 1명 이상 |

**분모 = 발급 시점의 현재 참가자 수.** 늦게 들어온 사람 때문에 **이미 받은 증표는 취소되지 않는다**(획득 시각 기록). 신고 인원(`size`)은 요금 계산에만 쓴다.

### 1:1 미션 (일대일 대응)
**미션 상대 = 나보다 바로 앞에 참여한 사람.** 참여하는 순간 `missionTarget` 한 필드에 확정 저장한다(첫 참가자는 두 번째 참가자가 들어올 때 확정). 친한 사람끼리만 찍는 걸 막는 장치.

> 매번 참가자 목록에서 원형으로 계산하면 사람이 들어올 때마다 **화면에 뜬 미션 상대가 바뀐다**(A4 감점). 필드 하나 저장으로 끝낸다.

## 2. 초대/동반 참여 없이는 안 되는 이유 (B3)

남의 QR을 찍어야 숫자가 오른다. 혼자면 0, 증표 0. **전원이 동시에 각자** 진행한다(릴레이처럼 한 번에 한 명만 활동하는 구조가 아님).

**성장 루프**: 호스트 1명 → 초대 링크 → 참여자 N명 → **참여자도 각자 자기 코드가 실린 링크를 공유**(참여자 1명이 다음 참여자를 데려오면 둘 다 +1) → 파티 후 `다음 파티 만들기`로 참여자가 다음 호스트가 된다. 공유 버튼이 아니라 숫자가 오르는 유일한 경로다.

3단계 시나리오의 2~3단계(초대 링크 복사 → 접속·참여·자동 태그·증표)가 그대로 B3 실동작 evidence다.

## 3. 단톡방·인스타·구글폼으로 안 되는 이유 (C3)

| 대체재 | 못 하는 지점 |
|---|---|
| 인스타 맞팔 | 파티 밖 관계까지 섞임. "이 파티에서" 만난 사람 수·진행률·증표·호스트 데이터 0 |
| 종이 스탬프 랠리 | 부스용이지 **사람용**이 아님. 사람마다 도장을 들고 다닐 수 없음 |
| Whova·Brella (컨퍼런스 앱) | 계정·수백만 원·사전 세팅. 파티 현장에서 즉석 생성 불가 |
| **Event Passport PRO** (플레이스토어 앱, 다운로드 10+) | 가장 가까운 대체재. **네이티브 앱 = 설치 마찰.** 방금 만난 사람에게 "이 앱 깔아 주세요"를 시켜야 하는 순간 태그가 안 일어난다. 다운로드 10+가 그 결과다 |
| 단톡방·구글폼 | 상호 선택을 **비밀로** 계산 못 함. 사람이 개입하는 순간 누가 누굴 골랐는지 새어 나감 |

**우리가 이기는 지점 2개**

1. **설치 0** — 링크 하나로 참여, 태그는 폰 기본 카메라가 URL을 여는 것으로 끝난다. 같은 아이디어(Event Passport PRO)가 다운로드 10+에서 멈춘 이유가 설치 마찰이라는 게 우리 가설이고, 그래서 우리는 앱을 만들지 않는다.
2. **상호 선택의 비밀** — "서로 고른 쌍일 때만 읽힌다"가 **Firestore 보안 규칙으로 강제**된다(13절). 운영자도, 개발자도, devtools를 연 참가자도 짝사랑을 볼 수 없다. 사람이 집계하는 구글폼·단톡방으로는 구조적으로 불가능하다.

> ⬜ 제출 전 Event Passport PRO 스토어 페이지를 한 번 열어 **설명 문구·최근 업데이트 날짜**를 확인하고 인용한다(투자자 페르소나는 대체재를 이름으로 대는 문서에 7점 이상을 준다). 제품명은 검색 충돌을 피해 한글 **"파티 패스포트"** 로 고정.

## 4. 다시 올 이유 (B4)

- 증표는 파티가 끝나도 **`내 증표함`에 남고 다음 파티에서 누적**된다. 로그인이 없으므로 **증표함은 브라우저 localStorage에 쌓인다**(같은 폰에서 다음 파티에 참여하면 이어짐). 포켓몬고 메달 구조.
- **트리거 시점**: 호스트가 `파티 종료`를 누른 직후(또는 생성 24시간 경과) 상호 선택 결과 화면이 열린다.
- 결과 화면 하단에 `다음 파티 만들기` — 참여자가 다음 호스트가 되는 경로.

> 계정 없이 기기 간 증표 이전은 안 된다. 문서에 "계정으로 누적"이라고 쓰지 말 것(구현 대조 6점 상한).

## 5. 타깃 고객 (B1) — ⬜ 제출 전 반드시 채운다

**관찰 인용이 없으면 6점 상한.** 아래 문장 틀에 오늘 안에 실명 수준 집단 + 답변 + 날짜를 넣는다.

```
⬜ <O월 O일> <OO대 OO동아리 회장 A / OO사 오프사이트 담당 B> 등 <N>명에게
   "처음 보는 사람이 많은 자리에서 말을 어떻게 트셨나요"를 물었더니
   "<직접 답변 인용>"이라고 답했다.
```

1차 타깃(셀 수 있는 집단): 대학 동아리·학과 신입 환영회 주최자, 50인 이상 기업의 오프사이트 담당자. "20대", "파티 하는 사람들" 같은 표현은 금지(3~4점).

## 6. 최초 유입 채널 (B2) — ⬜ 제출 전 반드시 채운다

**모수·주체·시점 중 둘이 없으면 5점 상한.** 채널 이름만 나열하면 4점.

```
⬜ <O월 O일> <팀원 이름>이 <에브리타임 OO대 게시판(일 활성 약 N명)>에 게시,
   <O월 O일> <OO 동아리연합회 단톡방(N명)>에 공유.
```

## 7. 수익 모델 (C1)

| 요소 | 값 |
|---|---|
| 지불 주체 | 파티 **호스트** |
| 지불 시점 | **파티 생성 시**, 신고 인원 20명 초과 시 |
| 금액 | **9,900원** (20명까지 무료) |

**가격 근거**: 컨퍼런스용 대체재(Whova 등)는 연 단위 수백만 원이라 1회성 파티에 못 쓴다. 그 아래 가격대가 비어 있다.
⬜ B1 인터뷰 때 **"파티당 9,900원이면 낼 의향이 있나"를 같이 묻고 답변 수(N명 중 M명)를 적는다** — 이게 있어야 7점을 넘는다.

**화면에 반드시 노출**: 파티 생성 화면에 `20명까지 무료 / 초과 시 9,900원` 한 줄. 결제 연동은 불필요하지만 **문구가 화면에 없으면 C1은 6점 상한**이다.

## 8. 시장 규모 — 상향식 (C2)

계산식 없이 TAM만 인용하면 3점 상한. 아래는 **가정을 전부 표기한 상향식**이다.

| 단계 | 값 | 근거 |
|---|---|---|
| 국내 대학생 수 | 190만 명 | 「가정」 교육통계 — ⬜ 제출 전 출처 확인 |
| 1인당 연간 모임 참여 | 6회 | 「가정」 |
| 평균 파티 인원 | 20명 | 「가정」 |
| → 연간 파티 건수 | 190만 × 6 ÷ 20 = **57만 건** | |
| 20명 초과(유료 대상) 비율 | 20% → 11.4만 건 | 「가정」 |
| 유료 전환율 | 10% → 1.14만 건 | 「가정」 유사 도구 벤치마크 |
| 단가 | 9,900원 | 7절 |
| **대학 세그먼트 연 매출** | **약 1.1억 원** | |

기업 오프사이트(50인 이상 사업체 약 4만 곳 「가정」 × 연 2회 × 전환 5%) = 4,000건 × 9,900원 ≈ **4천만 원**.
**합계 약 1.5억 원/년.** 확장 경로: 축제·페스티벌 부스 단위 판매 → 행사 대행사 B2B(건당 단가 10배).

## 9. 단위 경제성 (C4) — 숫자

파티 1건 = 20명 · 2시간 · 만남 40건 「가정」, Firestore `onSnapshot` 기준.

| 항목 | 수치 |
|---|---|
| 문서 쓰기 | 약 80건 → $0.18/10만 → **0.2원** |
| 문서 읽기 | 약 2,400건 → $0.06/10만 → **2원** |
| 호스팅 | GitHub Pages **0원** |
| **파티 1건당 서버 비용** | **약 2.2원** (환율 1,400원/$ 「가정」) |
| 무료 티어 소화량 | 5만 reads/일 ÷ 2,400 ≈ **하루 20파티까지 0원** |
| 운영 인력 | **0명** — 생성·초대·태그·증표·종료·결과 전부 자동 |
| 마진 | 9,900원 − 2.2원 ≈ **99.9%** |

**폴링을 쓰지 않는 이유(숫자)**: 3초 폴링이면 폴링 1회당 (참가자 수 + 만남 수)만큼 읽는다. 20명이면 1,200 reads/3초 → **무료 티어 5만 reads가 약 2분에 소진**되고 화면이 멈춘다(A1·A2 즉사). 유료 환산 시 파티 1건 약 2,400원. `onSnapshot`은 바뀐 문서만 과금돼 **1,000분의 1**이고 코드도 더 짧다.

## 10. 제출 3단계 시나리오 (submission-guide 형식)

```
1단계 — 첫 화면에서 "파티 만들기" 버튼을 누르고 "파티 이름"에 "금요일 파티"를 입력한 뒤 "파티 만들기"를 누른다. "초대 링크가 생성되었습니다"가 보이고 주소가 /party/로 바뀌면 성공
2단계 — "초대 링크 복사" 버튼을 누른다. "복사되었습니다"가 보이고 화면에 초대 링크(URL)가 표시되면 성공
3단계 — 표시된 초대 링크로 접속해 "이름"에 "김서준"을 입력하고 "참여하기"를 누른다. "참여 완료"와 "만난 사람 1명", "첫 만남 증표"가 보이면 성공
```

**3단계에서 에이전트가 추가로 할 동작은 0개다.** 초대 링크에 초대자 코드가 실려 있어 참여 즉시 자동 태그되고, 그 결과로 진행률·증표가 화면에 뜬다. 이 한 줄 덕분에 태그·만난 사람 수·증표가 evidence에 남고 **B3·B4·C3·D가 6점 상한에서 풀린다.**

**파티 종료·상호 선택 화면은 시나리오에 넣지 않는다.** 단계가 무거워질수록 실패 확률만 오른다.
심사 에이전트가 A3(기획안 대비 구현)를 확인할 수 있게 태그는 **`코드로 태그` 4자리 입력**으로도 동작한다 — Playwright는 카메라로 QR을 못 찍는다.

### 화면 텍스트 (글자 단위 고정)
`파티 만들기` · `파티 이름` · `초대 링크가 생성되었습니다` · `초대 링크 복사` · `복사되었습니다` · `이름` · `참여하기` · `참여 완료` · `만난 사람` · `첫 만남` · `내 코드` · `코드로 태그` · `파티 종료` · `다시 만나고 싶은 사람` · `선택 제출` · `서로 선택된 사람` · `다음 파티 만들기` · `내 증표함`

## 11. 구현 규칙 (엔지니어 페르소나 대비)

| # | 함정 | 처리 |
|---|---|---|
| 1 | 클립보드가 2단계를 죽인다 — `navigator.clipboard.writeText`는 문서에 포커스가 없으면 reject | `try/catch`로 감싸고 **실패해도 `복사되었습니다` 토스트와 URL 텍스트를 노출** |
| 2 | 폰 기본 카메라가 **다른 브라우저**로 URL을 연다 (카톡 인앱 → Safari) → localStorage에 신원이 없음 | 태그 URL 진입 시 신원이 없으면 **`내 코드` 4자리 입력 폴백 화면** 1개 |
| 3 | 4자리 코드 충돌 | 파티 내 유일성 검사 후 재발급 |
| 4 | 자기 자신 태그·중복 태그 | 문서 ID를 정렬된 쌍 `a_b`로 만들고 `a === b`면 거부 |
| 5 | 24시간 자동 종료에 Cloud Functions를 쓰면 **유료 플랜** | 서버 작업 없이 클라이언트가 `createdAt + 24h`로 판정 |
| 6 | 새 탭·`alert`·`confirm`·호버 메뉴 | 0건 |
| 7 | 모바일 375px · 콘솔 에러 | 에러 0, 가로 스크롤 0, 빈 상태·잘못된 초대 링크 안내 화면 |

## 12. 남은 시간에 완주 가능한가

| 시각 | 마일스톤 |
|---|---|
| +0:10 | **빈 페이지라도 배포 URL 확보** |
| +0:50 | 1~3단계 동작 (생성 · 초대 링크 복사 · 참여 · **자동 태그 · 만난 사람 수 · 첫 만남 증표**) — **A1은 여기서 끝남** |
| +1:20 | QR · `코드로 태그` · 진행률 · 나머지 증표 · 미션 상대 · 요금 안내 한 줄 |
| +1:45 | 파티 종료 · 다시 만나고 싶은 사람 · 서로 선택된 사람 · 내 증표함 |
| +2:00 | 빈/에러 상태, 모바일 375px, 콘솔 에러 0 |
| +2:10 | Playwright로 배포 URL 3단계 검증 → 배포 프리즈 |

- 1~3단계는 PARTY MOOD와 **거의 같은 코드**(생성·초대·참여). 추가분은 참여 시 meets 문서 1건 쓰기뿐.
- QR = URL 한 줄 + `qrcode.react` 컴포넌트 하나. 인앱 스캐너 없음(폰 기본 카메라가 URL을 연다).
- 태그·증표·미션은 순수 함수(집합 연산) + Firestore 문서 3종. **실시간 소켓 없음, 폴링 없음 — `onSnapshot`.**
- **시간이 밀리면 "파티 후"부터 자른다.** 태그·증표까지만으로도 B3·B4·D 성립. 문서에는 배포에서 동작 확인된 기능만 쓴다.

## 13. 저장소 · 보안 규칙

Firebase Firestore(무료, 스키마 없음) — 서로 다른 폰이 같은 참가자 목록·만남 기록을 봐야 하므로 필수. GitHub Pages는 정적. **PARTY MOOD도 동일하게 필요**(참가자 버튼 → 호스트 화면).

```
parties/{id}                    { name, size, createdAt, endedAt }
parties/{id}/participants/{pid} { name, code, missionTarget, joinedAt }
parties/{id}/meets/{a_b}        { a, b, at }         // a<b 정렬 → 무방향·중복 불가
parties/{id}/picks/{a_b}        { a: true, b: true } // 각자 자기 쪽 필드만 merge
```

**상호 선택은 규칙으로 강제한다.** 픽을 개인 문서에 저장하면 devtools로 짝사랑이 다 보인다(참가자 20명이면 해시도 무의미). 쌍 문서 + 아래 3줄이면 백엔드 없이 "서로 고른 쌍일 때만 읽힘"이 성립한다.

```
match /parties/{p}/picks/{pair} {
  allow create, update: if true;
  allow get:  if resource.data.size() == 2;   // 양쪽 다 골랐을 때만 읽힘
  allow list: if false;                       // 목록 조회 금지
}
```

> 자가 채점표는 의도적으로 뺐다. 점수 판정은 이 명세를 입력으로 **별도 세션에서 [personas](../personas/) 3종 검증**을 돌린다.
> 남은 ⬜ 5개(B1 인터뷰 인용 · B2 커뮤니티 모수/주체/날짜 · C1 지불 의사 응답 수 · C2 대학생 수 출처 · Event Passport PRO 스토어 문구)는 코드보다 먼저 채운다 — B·C의 30%가 여기 걸려 있다.

## PARTY MOOD(파티 감정 온도계)와 비교 — 의견

| 항목 | PARTY MOOD | 파티 패스포트 |
|---|---|---|
| D 게이트 | 10 — 진행 중에만 의미 | 8~10 — 상호 선택 문구를 "다시 만나고 싶은 사람"으로 고정해야 함 |
| A 완주 위험 | 낮음 (버튼 4개 + 카운터) | 중간 — 1~3단계는 거의 동일, 추가분은 meets 1건 쓰기 |
| 핵심 기능이 3단계 안에 있나 | ✅ `어색하다` 버튼이 3단계에 포함 | ✅ **v2에서 자동 태그·증표를 3단계에 포함**(v1은 ❌ → B3·C3가 6점 상한이었다) |
| B3 확산 | **7** — 1명이 눌러도 제품은 그대로 돌아감 | **9~10** — 혼자면 기능 자체가 0 + 참여자가 다음 초대자 |
| B4 리텐션 | 6 — 온도 그래프 리포트 (호스트만 볼 이유) | 8 — 증표 누적 + 결과 공개 |
| 참가자 쪽 사용 이유 | 약함 (문서에서 스스로 인정) | 강함 — 증표·미션·결과가 참가자 것 |
| C3 | 7~8 — "단톡방에 어색하다고 안 쓴다", 슬라이도 지목 | 8 — 대체재 4종 + 보안 규칙으로 뒷받침 |
| C4 | 폴링 기준이면 동일한 무료 티어 리스크 | `onSnapshot` 기준 파티당 2.2원 (9절) |

**전환 판단**: v1 상태로는 B3가 6점 상한에 걸려 온도계보다 나을 게 없었다. 10절(3단계에 태그 포함)을 실제로 구현해야만 이 표의 "수선 후" 점수가 성립한다.
아래 항목은 **어느 주제를 만들든 그대로 적용된다**: 11절 클립보드 예외 처리, 9절 폴링 → `onSnapshot`, 요금 문구 화면 노출.
