## 파티 같았던 해커톤

개발 시간이 단 3시간 남짓이었다. 참가자 모두 구글의 알록달록한 색에 맞춘 드레스코드로 모였고, 개발하는 내내 앞에서 DJ가 디제잉을 했다. 해커톤이라기보다 정말 파티 같은 분위기에서 코드를 짰다.

당일 공개된 주제는 **"파티를 더 잘 즐길 수 있는 서비스 만들기"**.

그리고 이번 해커톤의 가장 큰 특징은 **심사위원이 사람이 아니었다는 점**이다. 창업가·엔지니어·투자자 역할의 AI Agent가 각각 세 번씩 총 아홉 번 채점하고, 서비스가 실제로 작동하는지는 **Playwright가 배포된 링크에 직접 접속해 눌러보며** 평가한다. 총점은 `주제 게이트 배율 × (0.34·A + 0.33·B + 0.33·C)`.

심사위원이 사람이라면 설득의 문제지만, 시스템이라면 **사양의 문제**다. 그래서 우리는 제품을 만들기 전에 채점기부터 분석하기로 했다.

## 1. 코드는 안 본다, 배포 링크로 심사한다

심사 방식 설명에서 하나가 귀에 꽂혔다. 에이전트는 코드를 보지 않고 **제출된 배포 링크에 직접 접속해서 써본다.** localhost에서 아무리 잘 돌아가도 0점이라는 뜻이다.

그래서 만들 제품이 정해지기도 전에 배포 체계부터 깔았다. 모든 기술 선택의 기준은 "지금 가장 빠른 길" 하나였다.

| 영역 | 선택 | 이유 |
|---|---|---|
| 프론트 | React + **GitHub Pages 직배포** | 별도 호스팅 셋업 없이 push가 곧 배포 |
| UI | **daisyUI** | 컴포넌트를 직접 만들 시간이 없음. 클래스만 붙이면 버튼·카드·모달이 나옴 |
| 서버 | **Spring Boot**, CORS 전면 개방 | 빌드 시간이 적절하고 가장 익숙한 스택. 새 스택 셋업에 시간을 태울 수 없었음 |
| DB | 직접 호스팅하는 서버에 PostgreSQL 급조 | 이미 있는 인프라 재사용 |
| 배포 | **Docker Hub 경유 CI/CD** | push → 빌드 → 이미지 푸시 → 컨테이너 교체 → 헬스체크 자동화 |
| 네트워크 | 도메인·인증서 **선행** | 프론트가 HTTPS라 API가 HTTP면 브라우저가 혼합 콘텐츠로 차단. 심사 에이전트도 브라우저다 |

**13:37, 주제 확정 한참 전에 배포 URL이 살아 있었다.** 마감 직전의 배포는 반드시 사고가 나는데, 실제로 이날 CI가 두 번 깨졌고 초반에 만들어둔 파이프라인 덕에 몇 분 만에 복구했다.

## 2. 채점기 역설계

주최측이 공개한 모든 것을 구조화했다. 세션 슬라이드, 심사 설명 녹취, 사전 공개된 공식 루브릭, 제출 페이지 실물까지.

**실효 가중치 계산** — 12개 세부 항목을 대분류 가중치와 곱해 실제 배점을 구했다.

| 순위 | 항목 | 실효 비중 |
|---|---|---|
| 1 | A1 핵심 플로우 완주 | **13.6%** |
| 2 | B3 파티형 확산 구조 | 9.9% |
| 2 | C1 수익 모델과 지불 의사 | 9.9% |
| 2 | C3 방어 가능성·차별점 | 9.9% |
| 5 | A3 기획안 대비 구현 일치도 | 8.5% |

**숨은 상한 규칙 추출** — 루브릭 본문에 박혀 있던 규칙들이 실제로는 가중치보다 무서웠다.

- "~할 계획이다"는 근거가 아니라 의도 → **5점 상한**
- 문서가 주장한 기능이 브라우저에서 확인 안 되면 → **6점 상한**
- 시장 규모는 상향식 계산 없으면 → **4점 상한** (외부 TAM 인용만이면 3점)

**페르소나 복제** — 창업가·엔지니어·투자자가 각 항목을 어떤 질문으로 읽는지, 어떤 문장을 근거로 인정하는지, 감점 트리거가 무엇인지를 문서 세 개로 만들었다.

**모델 다양화로 헤지** — 실제 심사가 어떤 모델로 돌아갈지는 알 수 없다. 특정 모델 하나에 맞춰 최적화하면 과적합이 된다. 그래서 경량 모델부터 여러 모델을 서브 에이전트로 돌려 교차 검증하는 구조로 만들었다. **모델이 달라도 같은 지적이 나오는 항목은 진짜 구멍이다.**

## 3. 아이디어 선정을 채점기에 위임

해커톤에서 아이디어는 절반이다. 그런데 우리는 이렇게 봤다 — **채점자가 정해진 기준대로 움직이는 시스템이라면, 각 아이디어가 받을 점수는 이미 정해져 있다.** 우리가 할 일은 토론으로 설득하는 게 아니라 그 점수를 미리 측정하는 것이다.

채점기를 만드는 동안 팀원들에게 부탁했다. "생각나는 아이디어를 전부 문서로 정리해 달라." 그렇게 모인 **아이디어 7개**를, "명세대로 완벽하게 구현한다"는 전제 아래 **각각 독립된 세션에서 병렬로 채점**했다. 구현력을 변수에서 빼고, 순수하게 "심사 구조 안에서 이 아이디어의 상한이 몇 점인가"만 쟀다.

감으로는 더 좋아 보이는 아이디어도 예외 없이 전부 돌렸다. 그 결과 최적값으로 나온 것이 **파티 패스포트**였다.

---

## 4. 파티 패스포트

> **"파티에서 말 건 사람 수가 패스포트의 도장이 된다."**

풀고 싶었던 문제는 **파티에 가서도 결국 아는 사람하고만 이야기하다 돌아오는 경험**이었다. 새로운 사람을 만나려고 간 자리인데 막상 도착하면 누구에게 먼저 말을 걸어야 할지 모르겠고, 결국 같이 온 친구 옆에만 붙어 있다 집에 오게 된다. 사람이 많이 모였다고 좋은 파티가 되는 건 아니다.

- 호스트가 만든 링크에 들어가 **이름만 적으면 참여 끝.** 앱 설치도 회원가입도 없음
- 새로운 사람을 만날 때마다 서로의 **QR을 태그**하면 "만난 사람 수"가 올라감
- 첫 만남 · 아이스브레이커 · 파티 피플 · 파티 마스터 · 미션 완료 · 재회 — **증표 6종** 수집
- 친한 사람끼리만 뭉치지 않도록 **1:1 미션 상대** 배정
- 파티 종료 후 다시 만나고 싶은 사람을 **비밀 선택** → 서로를 동시에 선택한 쌍에게만 공개
- 증표는 파티가 끝나도 **내 증표함**에 영구 누적

이 아이디어가 1위였던 이유는 채점표와 맞물려 있다. "초대·동반 참여 없이는 제품이 성립하지 않아야 10점"이라는 확산 구조 항목에 구조적으로 부합하고, 태그 → 증표 → 상호 매칭이 **전부 브라우저에서 검증 가능한 동작**이다.

## 5. 사용자는 Playwright다

이전 회차에 투표 버튼을 "좋아요"라고 써서 에이전트가 투표로 인식하지 못해 점수를 날린 팀이 있었다고 한다. 우리 화면의 1차 사용자는 사람이 아니라 자동화 브라우저였다.

- **Depth 최소화** — 첫 화면에서 3단계 안에 핵심 가치 도달, 로그인·회원가입 없음
- **제출 시나리오의 문장 = 화면의 텍스트, 글자 단위 일치** — "파티 만들기", "복사되었습니다", "참여 완료", "만난 사람 1명"
- **에이전트는 QR을 못 찍는다** → "코드로 태그" 4자리 직접 입력 폴백을 1급 기능으로
- 시맨틱 마크업 + `aria-label` + `data-testid`, 모달·비활성화 게이트 제거
- 완주 경로 **콘솔 에러 0** (데스크톱·모바일 실측)

3단계 시나리오 자체도 설계였다. 2~3단계에 초대 링크 접속과 참여를 넣어, **완주(A1)를 통과하는 순간 확산 구조(B3)의 "브라우저 실동작 확인" 상한 조건이 같이 풀리게** 만들었다.

## 6. 자가 채점 루프 — 6.44점에서 시작

제출물이 나온 뒤, 역설계해둔 페르소나 3개로 **독립 자가 채점**을 돌렸다. 평균 **6.44점**. 처음부터 좋은 점수는 나오지 않는다. 여기서부터가 본 게임이었다.

읽는 프레임은 두 가지였다.

- **편차가 0인 항목이 진짜 구멍이다.** 구현 일치도(6·6·6), 타깃 구체성(6·6·6), 시장 규모(6·6·6) — 렌즈가 달라도 같은 결론이면 확실한 실점 지점
- **편차가 큰 항목은 검증 방법의 차이다.** 배포·안정성이 9·5·9로 갈렸는데, 엔지니어 채점만 라이브 API를 직접 두드려 500 에러를 발견했기 때문이다. 실제 심사는 브라우저를 직접 조작하니 **엔지니어 판정에 수렴한다**고 보고 그쪽을 기준으로 잡았다

### 비즈니스 모델 — 가장 기억에 남는 복기

파티라는 주제 특성상 짧은 시간에 그럴듯한 BM을 세우기 어려웠다. 처음엔 데이팅앱처럼 "파티 종료 후 서로 호감을 표시하고, 나에게 온 호감을 확인할 때 결제"를 생각했다.

그런데 이건 **에이전트가 테스트할 수 없는 기능**이다. 루브릭상 브라우저에서 확인 안 되는 주장에 기대는 항목은 상한에 걸린다. 그래서 **파티 인원 초과 시 유료 옵션**으로 방향을 바꾸고, **결제 화면을 mock으로 구현해 20명 초과면 결제 단계를 실제로 지나가게** 만들었다. 다시 채점기에 돌리니 점수가 유의미하게 올랐다. 지불 주체·시점·금액이 화면에 존재하는 순간, "문서상 주장"이 "검증된 구현"으로 바뀐 것이다.

### 이 루프에서 고친 15건 (일부)

| 지적 | 조치 |
|---|---|
| 상호선택 API 500 | 기존 데이터가 있는 테이블에 NOT NULL 컬럼이 추가되지 못한 스키마 드리프트 해소 |
| 정원·결제가 문서에만 존재 | 화면 구현 + **서버에서 402로 강제** (API 직접 호출 우회 차단) |
| 초대 링크 첫 진입 404 | 정적 호스팅 폴백 문제 → 링크를 루트 쿼리 형태로 변경 |
| 미션 상대에 초대자가 배정 | 대화 없이 완료되던 로직 교정 |
| 원가 근거가 코드와 400배 차이 | 폴링 횟수 반영해 재산정 |
| 문서의 미래형 문장 | "할 계획이다"를 확보한 권한과 확인된 사실로 교체 |
| 타 파티 참가자 ID로 태그 통과 | 요청마다 파티 소속 검증 |
| 24시간 마감이 표시 전용 | 마감 이후 제출을 서버에서 거부 |

## 7. 제출물은 문서가 아니라 심사관의 입력 프롬프트다

제출 페이지의 HTML을 그대로 떠서 분석했다. 팀 정보, 서비스 URL, 핵심 플로우 3단계, 기획안(8,000자), 발표 스크립트(4,000자) — 이 폼에 넣는 텍스트가 **그대로 심사 에이전트의 입력 프롬프트가 된다.**

그 관점으로 제출물을 다시 썼다. 사람 심사위원에게 내는 "잘 쓴 기획서"가 아니라, **에이전트가 가장 잘 알아듣는 형태** — 루브릭 항목명을 소제목으로 그대로 쓰고, 주장마다 숫자·고유명사를 붙이고, 화면에서 확인 가능한 사실만 남기고, 쉽고 논리적인 문장으로 우리 프로젝트가 이 주제의 정답임을 설득하는 텍스트.

## 배운 것

1. **평가자가 시스템이면, 시스템의 사양이 곧 요구사항 명세다.** 루브릭의 가중치·상한·게이트를 숫자로 환산하니 시간 배분이 저절로 정해졌다
2. **아이디어 선정도 측정의 대상이다.** 결정론적 채점 앞에서 각 아이디어의 점수는 이미 정해져 있다. 7개를 병렬로 돌려 최고점을 뽑았을 뿐, 인간의 감으로 고르지 않았다
3. **평가자를 복제하고, 모델 불확실성은 다양화로 헤지하라.** 여러 모델의 교차 검증에서 일치하는 지적이 진짜 구멍이다
4. **점수가 안 나오면 채점기의 입장에서 복기하라.** "테스트할 수 없는 기능"을 "화면에서 지나갈 수 있는 mock"으로 바꾸는 것만으로 점수가 움직인다
5. **화면도 문서도 전부 프롬프트다.** UX의 사용자가 Playwright이듯, 기획안의 독자는 LLM이다
6. **인프라를 먼저 깔면 피벗이 싸진다.** 배포 URL·서버·CI/CD를 주제 확정 전에 끝내둔 것이 3시간짜리 본 게임을 가능하게 했다
