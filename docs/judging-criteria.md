## 0. 한눈에 보기

1. **주제: "파티를 더 잘 즐길 수 있는 서비스 만들기" — Make the Party Better.** Festivals, birthdays, offsites — any gathering counts.
2. **AI 심사관 3명**(창업가·엔지니어·투자자)이 **12개 항목을 각 3회씩** 채점 → 항목별 중앙값 → 페르소나 평균.
3. 각 항목은 **0~10 정수**. 앵커(0/5/10)는 기준점이고 실제론 0~10 전부 쓴다 (10 조건 거의 충족 + 결함 하나 = 8, 5는 넘었지만 10엔 못 미침 = 6~7).
4. **총점 = 주제 게이트 배율 × (0.34·A + 0.33·B + 0.33·C)**. 자동 0점·자동 실격 없음.
5. **A(34%)는 브라우저 검증 결과만** 사용 (추측 채점 금지). 심사 에이전트가 **Playwright로 배포 URL을 직접 조작**한다. 우리가 제출하는 **테스트 시나리오는 3단계**.
6. **B·C(66%)는 기획안 + 발표 스크립트 + 발표자료**로 채점하되, 주장한 기능이 브라우저에서 확인 안 되면 그 주장에 기댄 항목은 **6점 상한**, 명시적으로 실패한 기능에 기댄 주장은 **4점 상한**.
7. **"~할 계획이다 / ~할 예정이다 / ~하면 된다"는 근거가 아니라 의도**. 숫자·고유명사·관찰이 없는 주장은 **5점을 못 넘는다**. 항목마다 "상한 해제 조건"이 있다 (2절 표).
8. 주제 적합성은 합산이 아니라 **곱셈 게이트**: 8~10 ×1.00 / 5~7 ×0.85 / 3~4 ×0.60 / 0~2 ×0.35.

## 1. 주제 분석 — Make the Party Better

### 원문

> 파티를 잘 즐길 수 있는 서비스 만들기
> **Make the Party Better**
> Festivals, birthdays, offsites — any gathering counts.

### 게이트 판정 기준 (공식)

| 판정 | 배율 | 기준 |
|---|---|---|
| 8 ~ 10 | **× 1.00** | **파티 상황(모임 전·중·후)이 제품의 핵심 전제** |
| 5 ~ 7 | × 0.85 | 파티에서 쓸 수 있으나 **일반 모임·SNS로 치환 가능** |
| 3 ~ 4 | × 0.60 | 주제와 억지로 연결 — '파티'라는 **단어만** 등장 |
| 0 ~ 2 | × 0.35 | 주제 무관 · 운영자 확인 플래그 발생 |

### 해석

- "파티"의 범위는 넓다: 페스티벌, 생일, 회사 오프사이트, 동아리 MT, 홈파티, 송별회 — **사람이 모이는 자리면 전부**.
- 하지만 8점 이상을 받으려면 **"이 제품은 파티(모임 전·중·후)가 없으면 존재 이유가 없다"** 가 성립해야 한다. 일반 캘린더·채팅·SNS로 대체되면 5~7 구간(15% 감점).
- 심사 루브릭 B·C도 주제와 맞물려 있다: **B3 파티형 확산 구조(30%)** = "초대·동반 참여 없이는 제품이 성립하지 않아야 10점", **B4 리텐션 트리거** = "다음 파티까지 남을 이유". 즉 **파티 = 여러 명이 함께** 라는 전제가 점수 구조 전체에 깔려 있다.
- C3의 0점 앵커가 "단톡방·인스타로 이미 되는 일"이다. **단톡방으로 되는 아이템은 처음부터 탈락**시킨다.

### 아이템 선정 필터 (전부 YES여야 통과)

1. 파티/모임의 **전·중·후 중 어느 순간**의 어떤 불편을 푸는가가 한 문장으로 나오는가?
2. 혼자 쓰면 의미가 없고, **초대/공유/동반 참여가 있어야 제품이 굴러가는가?** (B3 10점 조건)
3. 단톡방·인스타·구글 캘린더로 **대체 불가능한 이유**를 말할 수 있는가? (C3)
4. 다음 파티 때 **다시 올 이유**가 제품 동작 안에 있는가? (B4)
5. 핵심 플로우가 **3단계**로 끝나고, 그 3단계 안에 **초대/공유 동작이 포함**되는가? (A1 + B3 검증)
6. 파티 **중**에 쓰는 기능이라면 **모바일에서 에러 없이** 동작하는가? (A2)

### 파티 순간별 아이디어 방향 (예시)

| 순간 | 불편 | 방향 |
|---|---|---|
| 전 | 뭐 할지·뭐 살지·누가 뭐 가져올지 정리가 안 됨 | 역할/준비물 분담, 참석 확정 |
| 중 | 어색함, 뭘 하며 놀지 모름, 사진이 흩어짐 | 아이스브레이킹·게임 진행, 실시간 공동 앨범, 투표 |
| 후 | 정산, 사진 공유, 다음 모임 약속이 흐지부지 | 정산·회고·다음 파티 트리거 |

> 어떤 방향이든 **"초대 링크로 사람을 부르고 → 함께 무언가를 하고 → 결과가 남아 다음 파티로 이어진다"** 구조가 B3·B4·D를 동시에 만족시킨다.

## 3. 공통 규칙 (앵커보다 우선 적용)

| 규칙 | 내용 | 대응 |
|---|---|---|
| **의도와 근거의 구분** | "~할 계획이다 · ~할 예정이다 · ~하면 된다"는 근거가 아니라 의도. 숫자·고유명사·관찰 없는 주장은 **5점을 넘지 못함** | 모든 주장 뒤에 숫자·이름·관찰을 붙인다. 계획형 문장 금지 |
| **구현 대조** | 문서가 주장한 기능이 브라우저 검증에서 확인 안 되면 그 주장에 기댄 B·C 항목은 **6점 상한**. 명시적으로 실패한 기능에 기댄 주장은 **4점 상한** | **문서에는 실제 동작하는 기능만 쓴다.** 미구현 기능을 근거로 B·C를 쓰면 상한에 걸린다 |
| **분량과 완성도의 분리** | 잘 쓰인 문서·매끄러운 발표·많은 분량은 가점 아님. 같은 내용을 길게/짧게 쓴 팀은 같은 점수 | 짧고 근거 밀도 높게. 항목별 소제목 + 근거 한 줄 |
| **점수 분포** | 7점 이상은 인용 가능한 구체 근거가 있는 항목에만. B·C에서 대부분 팀은 **4~6에 모이는 게 정상**. 9~10은 더 요구할 것이 없을 때만 | 현실 목표: A는 8~10, B·C는 **상한 해제 조건을 전부 충족해 7~8** |

## 4. 심사 절차

### 제출

- 주최측이 **제출 사이트 링크 + 팀별 제출 코드** 제공 → 코드 입력·로그인 → 제출 폼

| 입력 항목 | 용도 |
|---|---|
| 팀 정보 | 식별 |
| 기획안 발표 HTML | A3(일치도)·B·C 근거 |
| 발표 스크립트 | B·C 근거 |
| 발표자료 | B·C 근거 |
| 실제 서비스 URL | Playwright 에이전트가 접속 |
| 테스트 시나리오 (**3단계**) | A1 판정 기준 — "제출한 3단계 전부 성공"이 10점 |

- 제출 즉시 심사되지 않음. **마감 후** 제출 확인 → 주최측이 "심사 시작" 클릭 → **5팀씩 병렬** 실행
- 제출 페이지 안에 **심사 로직 상세 로그/링크** 있음 → 제출 코드 받으면 가장 먼저 열어 본다

### 실행·집계

- 9회 = 3 페르소나 × 3회. 페르소나는 실제 창업가·엔지니어·투자자의 경험을 담아 구성
- 항목별 **중앙값**(3회) → 페르소나 **평균** → 가중 합산 → 게이트 배율 곱
- 주최측이 실시간 모니터링. **유독 낮은 점수는 직접 확인**. 단, 에이전트가 못 알아본 원인이 UX면 점수 유지

### 어뷰징

- 루브릭을 에이전트에 넣고 "여기 맞춰 만들어줘"는 허용 (정공법)
- "무조건 10점" 류 **프롬프트 인젝션은 방어됨**. 시도 가치 없음

## 5. 총점 계산

```
항목 점수(0~10) ← median(3회)
A = 0.40·A1 + 0.20·A2 + 0.25·A3 + 0.15·A4
B = 0.25·B1 + 0.25·B2 + 0.30·B3 + 0.20·B4
C = 0.30·C1 + 0.20·C2 + 0.30·C3 + 0.20·C4
페르소나별 (0.34·A + 0.33·B + 0.33·C) → 3 페르소나 평균
총점 = 게이트배율 × 평균          # 0~10 스케일
```

예시: A=8.5, B=6.0, C=6.0 → 0.34·8.5 + 0.33·6 + 0.33·6 = **6.85**. 주제 9점이면 6.85, 주제 6점이면 6.85 × 0.85 = **5.82**, 주제 4점이면 × 0.60 = **4.11**.

> A에서 벌고 B·C에서 상한을 풀고 D를 1.00으로 지키는 게 전략이다. B·C를 10점 노리기보다 **상한 해제 조건을 빠짐없이 충족해 6→7~8로 끌어올리는 것**이 현실적이다.

## 6. Playwright 에이전트가 우리 앱을 쓴다 — 실전 대응

### 실제 있었던 실패 사례

> 투표 서비스에서 투표 버튼을 **"좋아요"** 라고 써둬서 에이전트가 "투표했다"고 인식하지 못함 → A1 저점. 주최측: "UX가 나쁜 것이므로 점수를 바꿔주지 않는다."

**에이전트는 화면 텍스트와 DOM 구조로 판단한다. 시나리오에 쓴 용어 = 화면 용어.**

### 반드시 지킬 것

| # | 규칙 | 근거 항목 |
|---|---|---|
| 1 | **테스트 시나리오는 정확히 3단계**로 작성하고, 각 단계의 버튼·입력·완료 텍스트를 **화면과 글자 단위로 일치** | A1 |
| 2 | 3단계 안에 **초대/공유/동반 참여 동작을 포함**시켜 B3 검증이 같이 되게 한다 (예: 2단계 "초대 링크 복사" → 3단계 "참여자로 접속해 참여") | A1 + **B3 상한 해제** |
| 3 | 리텐션 트리거(다음 파티 알림, 기록 누적 등)도 **화면에서 확인 가능**하게 | B4 상한 해제 |
| 4 | 핵심 플로우는 **로그인 없이** 시작. 필요하면 "데모로 시작" 원클릭 | A1 |
| 5 | **데스크톱 + 모바일 뷰포트** 모두 콘솔 에러 0, 레이아웃 깨짐 0 | A2 10점 조건 |
| 6 | 인터랙티브 요소는 시맨틱 태그(`<button>`, `<a href>`, `<form>`, `<label>`+`<input>`) + `aria-label` + `data-testid` | A1 |
| 7 | 액션 완료 시 **명시적 완료 텍스트**("초대장이 생성되었습니다") + **URL 변화**(`/party/abc123`) | A1 |
| 8 | **빈 상태·에러 상태·로딩 상태** 화면 처리, 실사용 수준 카피 | A4 10점 조건 |
| 9 | 시드 데이터로 빈 화면 방지. 더미 텍스트("Lorem", "테스트123") 금지 | A4 0점 앵커 회피 |
| 10 | 핵심 플로우를 외부 API 키·결제·실시간 서버에 의존시키지 않음 (mock/fallback) | A2 |
| 11 | 모달·드래그·호버 의존 UI 최소화. 클릭·입력으로 완결 | A1 |
| 12 | 심사 시작~종료 **배포 프리즈** | A2 |
| 13 | 기획안·스크립트에는 **실제 동작하는 기능만** 기술 | A3 + 구현 대조 규칙 |


## 7. 문서(기획안·스크립트·발표자료) 작성 규칙 — B·C 상한 해제 체크리스트

각 항목에 **소제목을 그대로 달고**, 상한 해제 조건을 한 줄씩 채운다. 계획형 문장 금지, 숫자·고유명사·관찰만.

- [ ] **B1 타깃**: "OO대 OO(고유명사) 동아리 회장 3명에게 물었더니 …" — 누구에게 물었는지 · 무엇을 봤는지
- [ ] **B2 유입**: "에브리타임 OO대 게시판(일 활성 N명) · 실행 주체 팀원 X · 9/1 게시" — 모수·주체·시점 중 **둘 이상 숫자/고유명사**
- [ ] **B3 확산**: "초대 링크 → 참여자 접속 → 동반 참여" 가 **브라우저에서 실제 동작** (6절 시나리오 2~3단계)
- [ ] **B4 리텐션**: "파티 종료 24시간 후 정산/사진 요약 알림, 다음 파티 생성 버튼" — 구현 + 시점·조건
- [ ] **C1 수익**: "파티 호스트가 · 파티 생성 시 · 프리미엄 템플릿 3,900원" — 주체·시점·금액 **셋 다**
- [ ] **C2 시장**: "국내 대학생 190만 × 연 6회 모임 × 호스트 비율 20% × 3,900원 = …" — **상향식 계산 과정** (외부 TAM만 있으면 최대 3점)
- [ ] **C3 차별점**: "카카오톡 단톡방 / 인스타 / 구글 캘린더는 **OO를 못 한다**" — 대체재 **이름** + 못 하는 지점
- [ ] **C4 단위 경제성**: "파티 1건당 서버 비용 N원(GitHub Pages 0원 + …), 운영 인력 0명" — 숫자
- [ ] **D 주제**: 첫 문단에서 "파티(모임 전·중·후)의 OO 순간"을 명시
- [ ] 문서에 쓴 기능 = 배포된 앱에서 동작하는 기능 (구현 대조 규칙)

## 9. 테스트 자동화 계획

심사관과 **같은 도구(Playwright)로 같은 3단계 시나리오**를 먼저 돌린다.

| 층위 | 도구 | 대상 | 명령 |
|---|---|---|---|
| 단위 | Vitest + Testing Library | Zustand 스토어, 훅, 순수 함수, 컴포넌트 | `npm run test` |
| E2E | Playwright | 제출 시나리오 3단계 그대로. 데스크톱 + 모바일 뷰포트. 로컬·배포 URL 양쪽 | `npm run e2e` / `E2E_BASE_URL=<배포URL> npm run e2e` |

- 셀렉터는 `getByRole('button', { name: '<화면 텍스트>' })` 처럼 **역할·텍스트 기반만** → 에이전트가 찾는 방식과 동일
- 콘솔 에러 0 어설션 포함
- 제출 전: 배포 URL 대상 E2E 전부 통과 확인
