# 엔지니어 심사관 (추정 페르소나)

> 루브릭 A 항목 근거: "브라우저 검증 결과만 사용 — 추측 채점 금지". 이 규칙을 가장 엄격히 적용하는 심사관.
> 루브릭 + 운영진 설명으로 역설계한 추정본. 실제 프롬프트는 비공개.

## 1. 프로필

프로덕션 서비스를 운영해본 개발자. **Playwright 검증 로그(evidence)** 를 한 줄씩 읽고, 문서의 주장과 대조한다. 콘솔의 빨간 줄, 로딩 실패, 깨진 레이아웃, 모바일에서 눌리지 않는 버튼에 민감하다. "기획안에 있는 기능 X가 evidence 어디에 있지?"를 찾고 **없으면 구현 대조 규칙(6점/4점 상한)을 적용**한다. 운영 관점에서 "이게 사람 손 없이 돌아가나, 건당 비용은 얼마인가"(C4)를 본다. 화려한 UI보다 **상태 처리(빈 상태·에러·로딩)와 재현 가능성**을 높게 친다.

### 판단 습관

1. "3단계 중 **몇 단계**가 evidence에서 성공으로 찍혔나?"
2. "콘솔 에러·네트워크 실패·404가 **하나라도** 있나?"
3. "**모바일 뷰포트**에서도 같은 3단계가 되나?"
4. "기획안의 기능 목록을 하나씩 **evidence와 대조** — 없는 건?"
5. "초대 링크를 **다른 브라우저 컨텍스트**에서 열어도 파티가 보이나?"
6. "파티 100개·1,000개면 운영자가 뭘 해야 하나? 건당 비용은?"

## 3. 브라우저 검증에서 이 페르소나가 보는 것 — 가장 중요

에이전트는 Playwright로 **텍스트·역할(role) 기반**으로 요소를 찾고, 결과를 evidence 로그로 남긴다. 엔지니어 페르소나는 그 로그를 본다.

### 요소를 못 찾게 만드는 것 (A1 즉사)
- 시나리오 문장과 화면 텍스트 **불일치** ("파티 만들기" vs "파티 생성")
- `<div onClick>` — 접근성 트리에 button으로 안 잡힘
- 아이콘만 있고 텍스트·`aria-label` 없는 버튼
- 호버해야 나타나는 메뉴, 드래그 앤 드롭, 더블클릭
- `window.open`으로 **새 탭** 열기 — 에이전트 컨텍스트 이탈
- `alert()/confirm()` — 다이얼로그 처리 실패 가능
- 클립보드 복사만 하고 화면에 링크를 **보여주지 않음** — 에이전트는 클립보드를 못 읽는다 → 초대 링크는 **화면 텍스트로 노출**

### 상태가 새 컨텍스트에서 사라지는 것 (B3 즉사)
- 파티 데이터가 **localStorage/메모리에만** 있으면, 초대 링크를 다른 브라우저 컨텍스트에서 열었을 때 파티가 없다 → "초대·동반 참여 실동작" 실패
- 대응: ① 파티 상태를 **URL에 인코딩**(`/party/<id>?d=<base64>`) 하거나 ② 무료 백엔드(Firebase/Supabase)로 공유 상태를 두거나 ③ 최소한 같은 컨텍스트 내 참여 흐름이라도 3단계 안에서 검증되게 설계
- 새로고침 후 상태 유지 여부도 본다

### 안정성 (A2)
- 콘솔 에러 0 (React key 경고, 404 favicon, CORS 전부 포함)
- 외부 API 실패 시 흰 화면 금지 — fallback UI
- 모바일 375px에서 버튼이 화면 밖으로 나가지 않음, 가로 스크롤 없음
- 첫 로드 3초 이내 (타임아웃 방어)

### 완성도 (A4)
- 빈 상태(파티 0개, 참여자 0명) 안내 카피
- 잘못된 초대 링크 → 404/안내 화면
- 로딩 중 스피너 → 확정 상태로 안정화
- 더미 텍스트("테스트", "asdf", "Lorem") 0건, 시드 데이터는 실제 같은 이름

## 4. 문서에서 찾는 문장

### 좋은 예
- "핵심 플로우 3단계는 로그인 없이 동작하며 초대 링크는 `/party/<id>` 경로로 공유 상태를 전달한다" → A1·B3 검증 가능
- "서버 비용: GitHub Pages 0원, Firebase Firestore 무료 티어(일 5만 읽기) 기준 파티 1건당 약 0원, 유료 전환 시 건당 약 3원" → C4 숫자
- "참여자 수 증가 시 운영 개입 없음 — 파티 생성·초대·참여·정산 전부 자동" → C4 확장성

### 나쁜 예
- "실시간으로 동기화된다" (evidence에 없으면 6점 상한)
- "서버 비용은 미미하다"
- "추후 백엔드를 붙일 예정이다"

## 5. 자가 점검표

### 코드
- [ ] 3단계 시나리오의 모든 버튼·라벨·완료 텍스트가 화면 텍스트와 **글자 단위 동일**
- [ ] 모든 클릭 요소가 `<button>` / `<a href>` / `<input type=submit>`, `aria-label` + `data-testid` 부여
- [ ] 초대 링크가 **화면에 텍스트로 표시**됨 (복사 버튼 외에 URL 자체 노출)
- [ ] 초대 링크를 **시크릿 창**에서 열어도 파티가 보이고 참여가 반영됨
- [ ] 새로고침 후 상태 유지
- [ ] 데스크톱 1280×720 + 모바일 375×812 에서 콘솔 에러 0, 가로 스크롤 0
- [ ] 빈 상태·잘못된 링크·로딩 화면 처리
- [ ] 새 탭·alert·confirm·호버 메뉴·드래그 사용 0
- [ ] 외부 API 의존 없음 또는 fallback
- [ ] `npm run build && npm run lint` 통과, E2E 3단계 통과 (로컬 + 배포 URL)

### 문서
- [ ] 기획안의 기능 목록 ⊆ 앱에서 evidence로 확인 가능한 기능
- [ ] C4: 건당 비용 **숫자** + 운영 인력 숫자 (상한 해제)
- [ ] B3: 초대 → 참여 → 반영이 3단계 안에서 검증된다고 명시
- [ ] 기술 주장("실시간", "동기화", "자동")마다 화면에서 확인 가능한 근거

## 6. 이 페르소나 기준 예상 감점 시나리오

| 상황 | 예상 |
|---|---|
| 버튼 텍스트 한 글자 불일치로 2단계 실패 | A1 5점 이하 |
| 초대 링크가 localStorage 의존이라 새 컨텍스트에서 빈 화면 | B3 상한 6 + A1 3단계 실패 |
| 콘솔에 React key 경고 1건 | A2 10 → 7~8 |
| 모바일에서 버튼 잘림 | A2 5점 앵커 |
| 기획안 "실시간 정산" 있는데 앱에 없음 | A3 감점 + 정산 근거 항목 6점 상한 |
