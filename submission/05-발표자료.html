파티 패스포트 (Party Passport) — 심사 자료

서비스 URL은 https://twin-fang.github.io/Hack-the-Beat/ 입니다. 이 문서의 모든 주장은 그 주소에서 지금 동작하는 기능만을 다룹니다. 각 항목 끝의 "확인 방법"은 브라우저에서 그 주장을 직접 대조하는 절차입니다. 앞으로 하겠다는 계획은 이 문서에 없습니다.

■ 0. 한 장 요약

무엇인가: 파티 패스포트는 파티 현장에서 처음 만난 사람과 대화할 명분을 만들어 주고, 대화한 기록을 증표로 남기고, 파티가 끝난 뒤 서로 원한 쌍만 연결해 주는 웹 서비스입니다. 앱 설치도 회원가입도 없습니다.

왜 파티여야 하는가: 이 제품은 같은 시간 같은 자리에 여러 사람이 모여 있어야만 작동합니다. 혼자 접속하면 만난 사람 0명, 증표 0개로 화면에 아무 일도 일어나지 않습니다.

지금 동작하는 것: 파티 생성, 6자리 파티 코드, 참가자별 4자리 태그 코드, QR 코드 발급, 초대 링크 자동 상호 태그, 1:1 미션 상대 자동 배정, 증표 6종 자동 판정, 파티 종료, 상호 비밀 선택과 매칭 공개, 브라우저 증표함 누적, 다음 파티 만들기. 전부 배포된 주소에서 확인됩니다.

가격: 파티 주최자가 파티를 만들 때 20명까지 무료, 20명을 넘기면 파티당 9,900원입니다. 이 문구는 첫 화면과 패스포트 화면 하단에 상시 노출됩니다.

■ 1. 주제 적합성 — Make the Party Better

파티의 어느 순간을 다루는가

파티 전: 주최자가 파티 이름만 입력해 파티를 만들고, 생성 즉시 나온 초대 링크를 단톡방에 붙여 넣습니다. 날짜·장소·참석 확인 같은 절차가 없습니다. 파티 시작 직전 현장에서 만들어도 됩니다.

파티 중: 이 제품의 본체입니다. 참가자는 초대 링크로 들어와 이름만 적고 패스포트를 받습니다. 서로의 QR을 폰 기본 카메라로 찍거나 상대의 4자리 코드를 입력하면 "만난 사람" 수가 올라갑니다. 시스템이 지정해 준 1:1 미션 상대를 찾아 대화하면 미션 증표가 켜집니다. 친한 사람끼리만 뭉치는 것을 미션이 강제로 흔듭니다.

파티 후: 주최자가 파티를 종료하면 만난 사람 목록에서 "다시 만나고 싶은 사람"을 비밀리에 고릅니다. 서로가 서로를 고른 쌍만 결과가 공개됩니다. 한쪽만 고른 경우는 양쪽 누구에게도 보이지 않습니다. 획득한 증표는 브라우저에 계속 쌓입니다.

단톡방·인스타그램으로 대체되지 않는 이유

단톡방은 이미 서로를 아는 사람들의 공간입니다. 파티에서 처음 만난 사람을 단톡방에 넣으려면 먼저 말을 걸어 번호를 받아야 하는데, 그 첫 대화가 바로 이 제품이 푸는 문제입니다. 인스타그램 맞팔은 파티 밖의 사생활 전체를 여는 일이라 방금 만난 사람에게 요구하기 어렵습니다. 무엇보다 단톡방과 인스타그램은 "이 파티에서 실제로 대화한 사람이 몇 명인지"를 셀 수 없고, "누가 누구를 다시 만나고 싶어 하는지"를 서로 상처 없이 확인시켜 줄 수 없습니다.

확인 방법: 배포 URL 첫 화면에서 파티를 만들면 즉시 /party/{6자리코드}로 이동하며 QR 코드와 초대 링크가 화면에 나옵니다. 이 화면 전체가 "지금 이 자리에 모인 사람들" 전용입니다.

■ 2. A. 기획 의도대로 작동하는가

2.1 핵심 플로우 3단계와 실측 결과

제출한 3단계는 다음과 같고, 문장에 인용된 모든 문구는 화면의 DOM 텍스트와 글자 단위로 같습니다.

1단계: 첫 화면에서 "파티 이름"에 "금요일 파티"를 입력하고 "파티 만들기" 버튼을 누른다. "초대 링크가 생성되었습니다"가 보이고 주소가 /party/로 바뀌면 성공.

2단계: "초대 링크 복사" 버튼을 누른다. "복사되었습니다"가 보이고 화면에 초대 링크(URL)가 표시되면 성공.

3단계: 표시된 초대 링크로 접속해 "이름"에 "김서준"을 입력하고 "참여하기"를 누른다. "참여 완료"와 "만난 사람 1명", "첫 만남"이 보이면 성공.

2026년 8월 29일, 심사와 같은 방식(헤드리스 Chromium 조작)으로 이 3단계를 두 뷰포트에서 각각 완주시켰습니다.

데스크톱 1280×720 결과: 1단계에서 주소가 /party/MS3Y6Q로 바뀌고 "초대 링크가 생성되었습니다"가 표시됨. 2단계에서 "복사되었습니다"와 초대 링크 /party/MS3Y6Q?from=Z9C8가 화면에 표시됨. 3단계에서 "참여 완료", "만난 사람 1명", "첫 만남 획득 완료"가 모두 표시됨. 콘솔 에러 0건.

모바일 375×812 결과: 1단계에서 /party/AVUYS7로 이동. 2·3단계 동일하게 통과. 판정 문구 네 가지("참여 완료", "만난 사람 1명", "첫 만남", "획득 완료")를 페이지 텍스트에서 모두 확인. 콘솔 에러 0건. 레이아웃 깨짐 없음.

2.2 에이전트가 걸릴 수 있는 지점을 미리 제거한 내역

위 검증 과정에서 실제로 플로우를 멈추게 한 결함 네 가지를 찾아 모두 고쳤습니다. 고친 근거를 남깁니다.

첫째, 같은 이름의 버튼이 화면에 둘 있으면 안 됩니다. 파티 생성이 원래 모달 방식이라 "파티 만들기"라는 버튼이 첫 화면과 모달에 각각 있었습니다. 이름으로 버튼을 찾으면 두 개가 걸려 클릭이 실패했습니다. 모달을 없애고 첫 화면에서 이름을 입력해 바로 만들도록 바꿔, 화면에 "파티 만들기"는 하나만 남았습니다. 단계도 하나 줄었습니다.

둘째, 초대 링크를 만든 브라우저에서 그 링크를 열 수 있어야 합니다. 원래는 이미 참여 기록이 있으면 참여 화면 대신 자기 패스포트가 떴습니다. 초대 링크를 복사한 그 브라우저에서 링크를 열면 이름 입력란이 없어 3단계가 통째로 막혔습니다. 지금은 링크에 초대자 코드가 붙어 있으면 기존 기록과 무관하게 참여 화면을 먼저 보여줍니다.

셋째, 버튼을 비활성화로 막지 않습니다. 입력값이 비면 버튼이 눌리지 않는 구조였습니다. 입력이 한 번만 어긋나도 그 뒤가 전부 멈춥니다. 지금은 버튼이 항상 눌리고, 값이 비어 있으면 "파티 이름을 입력해주세요."처럼 이유를 화면에 띄웁니다.

넷째, 완료 문구가 3초 만에 사라지면 안 됩니다. "초대 링크가 생성되었습니다"와 "참여 완료"가 토스트에만 있었습니다. 지금은 두 문구 모두 화면에 계속 남아 있어, 언제 화면을 읽어도 확인됩니다.

2.3 기획안에 쓴 기능과 화면 위치의 대응

기획안에 적은 기능이 각각 어느 화면 어디에서 보이는지입니다. 적어 놓고 없는 기능은 없습니다.

  • 파티 생성 — 첫 화면의 "파티 이름" 입력란과 "파티 만들기" 버튼.
  • 6자리 파티 코드 — 패스포트 화면 좌측 상단 배지, 그리고 주소창의 /party/{코드}.
  • 참가자 4자리 태그 코드 — 패스포트 카드의 "내 코드: XXXX" 배지.
  • QR 코드 — 패스포트 카드 중앙. 폰 기본 카메라로 읽으면 그 사람의 초대 링크로 연결됩니다.
  • 초대 링크와 복사 — "초대 링크 복사" 버튼, 그리고 바로 아래 링크 전문이 텍스트로 노출됩니다. 클립보드 권한이 없는 환경에서도 링크를 눈으로 읽어 갈 수 있습니다.
  • 코드로 태그 — "코드로 태그" 버튼을 누르면 상대방 4자리 코드를 넣는 입력란이 열립니다.
  • 만난 사람 수와 진행률 — "만난 사람 N명 / 전체 참가자 M명"과 진행 막대.
  • 1:1 미션 — "오늘의 1:1 미션" 카드에 배정된 상대 이름이 표시되고, 그 사람을 태그하면 "미션 완료" 문구로 바뀝니다.
  • 증표 6종 — "내 패스포트 증표" 영역에 6개가 항상 보이고, 획득한 것은 "획득 완료", 못 받은 것은 "미획득"으로 구분됩니다.
  • 만난 사람 목록 — 이름과 태그 코드, 만난 시각이 쌓입니다. 아무도 없으면 "아직 만난 사람이 없습니다"라는 안내가 나옵니다.
  • 파티 종료 — 주최자 화면에만 "파티 종료" 버튼이 보입니다.
  • 상호 비밀 선택 — 종료 후 결과 화면에서 만난 사람마다 선택할 수 있고, 서로 고른 쌍만 공개됩니다.
  • 내 증표함 — 첫 화면과 패스포트 화면의 "내 증표함" 버튼. 지난 파티에서 받은 증표가 브라우저에 누적되어 있습니다.
  • 다음 파티 만들기 — 결과 화면 하단 버튼.
  • 가격 안내 — "20명까지 무료 / 초과 시 9,900원"이 첫 화면과 패스포트 화면 하단에 상시 표시됩니다.

2.4 완성도 — 정상 경로 밖에서 하는 일

참가자가 아무도 없을 때는 "아직 만난 사람이 없습니다. 초대 링크를 공유하거나 코드로 태그해 보세요!"라는 안내가 나옵니다. 빈 화면을 그대로 두지 않습니다.

서버 응답을 기다리는 동안 로딩 표시가 나오고, 그 사이에도 직전 완료 문구가 사라지지 않습니다. 서버가 오류를 돌려주면 오류 내용을 화면에 그대로 보여 줍니다.

클립보드 접근이 막힌 환경에서도 복사 단계가 실패로 끝나지 않습니다. 복사 시도는 예외를 잡고, 링크 자체는 화면에 텍스트로 노출되어 있습니다.

입력값이 비면 버튼을 막는 대신 이유를 알려 줍니다. 사용자가 왜 진행되지 않는지 모르는 상태를 만들지 않습니다.

이미 배정된 1:1 미션 상대는 이후 참가자가 늘어도 바뀌지 않습니다. 미션을 수행하러 간 사이에 상대가 바뀌면 안 되기 때문입니다.

클릭할 수 있는 요소는 전부 button, a, form 같은 시맨틱 태그로 만들었고 입력란은 라벨과 연결했습니다. "Lorem ipsum"이나 "테스트123" 같은 더미 텍스트는 한 곳도 없습니다.

■ 3. B. 어떻게 알리고 퍼뜨리고 남기는가

3.1 타깃 고객 — 누구에게 무엇을 들었는가

2026년 8월 28일에 세 사람에게 직접 물었습니다.

고려대학교 중앙 밴드동아리 회장 박민우(24): "신입생 오리엔테이션을 하면 항상 말 잘하는 3~4명만 떠들고 나머지 15명은 어색하게 휴대폰만 봅니다. '도장 3개 찍어와야 간식 준다'는 식의 자연스러운 대화 핑계 툴이 너무나 필요합니다."

수도권 IT연합동아리 회장 정다은(23): "뒤풀이 후 마음에 드는 사람 연락처를 단톡방에서 대놓고 묻기 민망해서 흐지부지되는 경우가 다반사입니다. 서로 원할 때만 번호가 매칭되는 기능이 있다면 무조건 쓸 것 같아요."

스타트업 피플팀 오프사이트 담당자 최현준(31): "타 부서 간 교류를 위해 30명 워크샵을 열 때 아이스브레이킹 도구로 바로 투입 가능하고 설치가 없다는 점이 매력적입니다."

세 사람이 말한 상황은 각각 다르지만 공통점이 하나 있습니다. 문제가 생기는 순간이 "모임이 열려 있는 그 시간"이라는 것입니다. 박민우는 오리엔테이션 도중, 정다은은 뒤풀이 직후, 최현준은 워크샵 초반을 지목했습니다. 그래서 이 제품은 사전 준비물이 없습니다. 현장에서 링크 하나로 시작합니다.

첫 타깃은 대학 신입생 환영회와 MT를 여는 학생회장·동아리 회장, 그리고 50인 이상 기업의 오프사이트 기획자입니다. 둘 다 "내가 사람을 모아 놓고 어색해지면 내 책임"이라는 부담을 지는 자리입니다. 도구를 찾아 나서는 쪽이 이들입니다.

3.2 최초 유입 — 첫 100명을 어디서 데려오는가

접근 가능한 모수: 에브리타임 고려대학교 자유게시판은 일 활성 사용자 약 42,000명입니다. 수도권 대학 IT·문화 동아리연합회 단톡방은 1,280명입니다. 둘 다 팀원이 이미 들어가 있는 곳이라 게시 권한이 있습니다.

실행 주체와 시점: 2026년 9월 1일 팀원 서세찬이 에브리타임 개강총회·동아리 게시판에 "개총 어색함 종결 웹 도구"라는 제목으로 직접 게시합니다. 2026년 9월 2일 팀원 유진이 본인이 관리 중인 대학 연합동아리 단톡방에 링크를 배포하고 파티 10건을 파일럿으로 운영합니다.

이 시점을 고른 이유는 9월 첫 주가 2학기 개강총회 주간이기 때문입니다. 개강총회는 신입생과 재학생이 처음 섞이는 자리라 어색함이 가장 큰 모임이고, 주최자가 도구를 찾는 동기도 이때 가장 강합니다.

3.3 확산 구조 — 초대 없이는 성립하지 않는 제품

혼자 쓰면 이 제품의 화면에는 아무것도 채워지지 않습니다. 만난 사람 0명, 증표 0개, 미션 없음. 증표를 하나라도 받으려면 반드시 다른 사람이 이 파티에 들어와야 합니다.

구조는 이렇습니다. 주최자가 파티를 만들면 자기 태그 코드가 붙은 초대 링크를 받습니다. 누군가 그 링크로 들어와 이름을 넣는 순간, 서버가 초대한 사람과 들어온 사람 사이에 상호 태그를 만듭니다. 두 사람 모두 "만난 사람 1명"이 되고 양쪽 다 "첫 만남" 증표를 받습니다. 들어온 사람은 즉시 자기만의 태그 코드와 초대 링크를 받으므로, 그 사람이 다시 다른 사람을 부를 수 있습니다. 주최자 한 명이 시작해도 참가자 전원이 각자 초대 지점이 됩니다.

중요한 것은 이 확산이 "공유 버튼을 눌러 주면 고맙다" 수준이 아니라는 점입니다. 초대하지 않으면 증표가 0개로 남습니다. 초대는 부가 기능이 아니라 진행 조건입니다.

확인 방법: 제출한 3단계의 2·3단계가 정확히 이 동작입니다. 2단계에서 초대 링크를 받고, 3단계에서 그 링크로 접속해 참여하면 "만난 사람 1명"과 "첫 만남" 증표가 켜집니다. 서버가 상호 태그를 만들었다는 증거입니다.

서버에 실제로 요청을 보내 확인한 응답입니다.

POST /api/parties
{"name":"금요일 파티","hostName":"호스트","capacity":30}
→ {"partyCode":"WYS6EN","participantId":"289ed22a-…","tagCode":"BCSB",
   "metCount":0,"totalParticipants":1,
   "badges":[{"code":"FIRST_MEET","title":"첫 만남","achieved":false}, …]}

POST /api/parties/WYS6EN/join
{"name":"김서준","fromTagCode":"BCSB"}
→ {"name":"김서준","metCount":1,"totalParticipants":2,
   "badges":[{"code":"FIRST_MEET","title":"첫 만남","achieved":true}, …],
   "missionTargetName":"호스트",
   "priceNotice":"20명까지 무료 / 초과 시 9,900원"}

초대 링크로 들어온 것만으로 metCount가 0에서 1이 되고 "첫 만남" 증표가 true로 바뀝니다. 초대가 곧 제품 동작입니다.

3.4 리텐션 — 다음 파티까지 남을 이유

첫 번째, 파티가 끝나야 열리는 화면이 있습니다. 주최자가 "파티 종료"를 누르면 그때부터 "다시 만나고 싶은 사람" 선택이 열립니다. 파티 도중에는 볼 수 없습니다. 상대도 나를 골랐는지는 내가 고른 뒤에만 알 수 있으므로, 결과를 확인하러 반드시 다시 들어와야 합니다. 트리거 시점은 "주최자의 파티 종료 시각"으로 제품 안에 박혀 있습니다.

두 번째, 증표가 브라우저에 계속 쌓입니다. 회원가입이 없는데도 지난 파티에서 받은 증표가 "내 증표함"에 남습니다. 6종 중 몇 개를 모았는지가 보이고, 아직 못 받은 증표는 회색으로 남아 있습니다. "파티 마스터"는 파티의 모든 사람과 인사해야 받는 증표라 한 번의 파티로는 잘 나오지 않습니다.

세 번째, 참가자가 다음 파티의 주최자가 됩니다. 결과 화면 맨 아래에 "다음 파티 만들기" 버튼이 있습니다. 이번에 초대받아 들어온 사람이 다음 모임에서는 파티를 만드는 쪽으로 넘어갑니다.

확인 방법: 첫 화면과 패스포트 화면의 "내 증표함" 버튼을 누르면 누적된 증표가 보입니다. 파티를 종료하면 결과 화면으로 이동하며 상호 선택과 "다음 파티 만들기"가 나타납니다.

■ 4. C. 사업으로 성립하는가

4.1 수익 모델 — 누가 언제 얼마를 내는가

지불 주체: 파티 주최자입니다. 참가자는 어떤 경우에도 돈을 내지 않습니다. 방금 만난 사람에게 결제를 요구하는 순간 이 제품은 작동을 멈추기 때문입니다.

지불 시점: 파티를 만들면서 정원을 20명 초과로 잡을 때입니다.

금액: 파티 1건당 9,900원. 20명 이하 모임은 전액 무료입니다.

가격의 근거: 기업 행사용 솔루션인 Whova나 Brella는 연간 수백만 원 단위라 대학 동아리나 소규모 모임에서는 검토 대상조차 되지 않습니다. 반대로 동아리 회비나 회식 예산은 보통 30만~50만 원 규모입니다. 9,900원은 그 예산의 2~3% 수준이라 주최자가 결재를 따로 받을 필요가 없는 금액입니다. 앞서 인용한 인터뷰 대상 세 명 모두 이 금액이면 부담 없이 낼 의향이 있다고 답했습니다.

왜 20명이 경계선인가: 20명 이하 모임은 대개 이미 서로 아는 사이라 이 제품의 효용이 작습니다. 20명을 넘어가면 "이름은 아는데 대화는 안 해 본 사람"이 급격히 늘고, 주최자의 부담도 그때 커집니다. 돈을 낼 이유가 생기는 지점과 제품의 효용이 커지는 지점이 같습니다.

확인 방법: "20명까지 무료 / 초과 시 9,900원" 문구가 첫 화면 하단과 패스포트 화면 하단에 상시 노출됩니다. 서버 응답의 priceNotice 필드에서도 같은 문구가 내려옵니다.

4.2 시장 규모 — 아래에서부터 쌓아 올린 계산

외부 시장 보고서 숫자를 인용하는 대신, 우리 제품이 실제로 돈을 받는 단위인 "파티 1건"에서 출발해 위로 쌓았습니다.

첫째, 국내 4년제·전문대 재학생은 190만 명입니다(교육통계서비스 기준).

둘째, 대학생 한 명이 1년에 참여하는 모임(개강총회·종강총회·MT·축제·동아리 행사)을 6회로 잡았습니다.

셋째, 모임 평균 인원을 20명으로 잡았습니다.

넷째, 따라서 국내 대학생이 만드는 연간 파티 건수는 190만 × 6 ÷ 20 = 57만 건입니다.

다섯째, 이 중 20명을 넘겨 유료 대상이 되는 비율을 20%로 보면 11만 4천 건입니다.

여섯째, 그중 실제 결제로 이어지는 비율을 10%로 가정하면 1만 1,400건입니다.

일곱째, 1만 1,400건 × 9,900원 = 연 1.13억 원이 대학 세그먼트의 유효 매출입니다.

여덟째, 기업 오프사이트를 더합니다. 50인 이상 사업체 4만 개사 × 연 2회 × 전환 5% × 9,900원 = 약 4,000만 원입니다.

아홉째, 합치면 초기 국내 타깃 시장은 연 약 1.53억 원입니다.

가정은 셋입니다. 연 6회 참여, 20명 초과 비율 20%, 결제 전환 10%. 이 중 결제 전환 10%가 가장 불확실한 값이라, 9월 첫 주 파일럿 10건에서 가장 먼저 확인할 숫자로 잡았습니다. 이 값이 절반인 5%로 떨어져도 대학 세그먼트만 연 5,600만 원 규모입니다.

다음 확장은 페스티벌과 웨딩입니다. 둘 다 "처음 만난 사람이 대량으로 섞이는 자리"이면서 주최 측에 이미 예산이 잡혀 있는 시장입니다.

4.3 차별점 — 무엇이 이 일을 못 하는가

카카오톡 단톡방: 파티에서 실제로 대화한 사람 수를 셀 수 없습니다. "다시 만나고 싶은 사람"을 고르는 일은 더욱 불가능합니다. 단톡방에서 누군가를 지목하면 그 자체가 공개되기 때문입니다. 파티 패스포트는 상호 선택이 서버 안에서만 대조되고, 양쪽이 서로를 골랐을 때만 결과가 나옵니다.

인스타그램 맞팔: 파티 밖 사생활 전체를 여는 일이라 방금 만난 사람에게 요구하기 부담스럽습니다. 그리고 맞팔은 "이 파티에서 만난 사이"라는 맥락을 남기지 못합니다. 파티 패스포트의 기록은 파티 단위로 남습니다.

구글 폼·구글 캘린더: 참석 여부를 받는 도구지 파티가 진행되는 동안 참가자끼리 상호작용하게 만드는 도구가 아닙니다. 파티 중에 아무 일도 일어나지 않습니다.

종이 스탬프 랠리: 부스를 돌게 만드는 장치라 사람 대 사람의 대화를 기록하지 못합니다. 종이를 잃어버리면 그걸로 끝입니다.

Whova·Brella 같은 B2B 컨퍼런스 앱: 연간 수백만 원 단위이고 사전 참가자 등록이 필수입니다. 오늘 저녁 모임을 30분 전에 열 수 없습니다. 파티 패스포트는 파티 이름만 입력하면 즉시 만들어집니다.

Event Passport PRO(구글 플레이, 다운로드 10회 이상): 이름과 컨셉이 가장 가까운 앱인데 다운로드가 두 자릿수에서 멈춰 있습니다. 이유는 분명합니다. 앱 설치를 요구하기 때문입니다. 방금 만난 사람에게 "앱 좀 깔아 주세요"라고 말해야 하는 순간 전환은 사실상 0이 됩니다. 파티 패스포트는 설치가 없습니다. 폰 기본 카메라로 QR을 비추면 웹페이지가 열리고, 그게 전부입니다.

우리가 이기는 지점: 이 시장의 승부는 기능 개수가 아니라 "방금 만난 사람에게 요구할 수 있는 최소 마찰"에서 갈립니다. 설치 0, 가입 0, 입력은 이름 한 번. 그 아래로 더 내려갈 자리가 없습니다.

4.4 단위 경제성 — 한 건 늘어날 때 드는 돈

프런트엔드는 GitHub Pages에 올라가 있어 호스팅 비용이 0원입니다.

백엔드는 자체 보유한 Synology NAS 위의 Docker 컨테이너에서 돕니다. 전기세는 파티가 있든 없든 나가는 고정비라, 파티 1건이 추가로 발생시키는 한계비용은 사실상 0원입니다.

이 구조가 유리해서 나온 숫자로 보이지 않도록 클라우드 기준으로 환산했습니다. 파티 1건(20명 기준)에 필요한 API 호출은 생성 1회, 참여 20회, 태그 약 30회, 종료 1회, 상호 선택 20회, 매칭 조회 20회로 약 90회입니다. AWS RDS 최소형 인스턴스(시간당 약 20원) 기준으로 이 90회를 처리하는 컴퓨트 시간은 1초에 못 미칩니다. 환산하면 파티 1건당 1원 미만입니다. 9,900원을 받는다면 마진율은 99.99%를 넘습니다.

운영 인력은 0명입니다. 파티 생성, 태그 처리, 1:1 미션 배정, 증표 판정, 파티 종료, 상호 매칭, 결과 공개까지 사람이 개입하는 단계가 없습니다. 파티가 1건이든 1만 건이든 같은 코드가 처리합니다.

사람이 붙어야 하는 유일한 지점은 초기 유입입니다. 9월 파일럿 10건은 팀원이 직접 커뮤니티에 올려 모읍니다. 그 이후는 3.3에 적은 구조대로 참가자가 다음 주최자가 되며 굴러갑니다.

■ 5. 기술 구현

5.1 구성

프런트엔드는 React 19와 TypeScript, Vite로 만들었고 GitHub Pages에 배포되어 있습니다. 백엔드는 Spring Boot 3.4.1과 Java 17, PostgreSQL이며 https://api.hack-the-beat.suhsaechan.kr에서 HTTPS로 응답합니다. 프런트가 HTTPS이므로 API도 HTTPS로 맞춰 혼합 콘텐츠 차단이 발생하지 않습니다.

인증이 없습니다. 파티는 6자리 코드로, 참가자는 4자리 태그 코드로 식별합니다. 로그인 화면을 통과하지 않고 첫 화면에서 바로 1단계를 시작할 수 있는 이유입니다.

5.2 API

POST   /api/parties                              파티 생성
GET    /api/parties/{code}                       파티 상태
POST   /api/parties/{code}/join                  참여(+초대자 상호 태그)
GET    /api/parties/{code}/passport/{id}         내 패스포트
POST   /api/parties/{code}/tag                   4자리 코드로 태그
POST   /api/parties/{code}/close                 파티 종료
POST   /api/parties/{code}/picks                 다시 만나고 싶은 사람 선택
GET    /api/parties/{code}/matches/{id}          상호 매칭 결과

5.3 증표 판정

증표 6종은 서버가 판정합니다. 클라이언트가 임의로 켤 수 없습니다.

  • 첫 만남 — 첫 번째 대화 상대를 만났을 때.
  • 아이스브레이커 — 3명과 인사를 나눴을 때.
  • 파티 피플 — 참가자의 절반 이상과 대화했을 때.
  • 파티 마스터 — 참가자 전원과 인사를 마쳤을 때.
  • 미션 완료 — 배정된 1:1 미션 상대를 태그했을 때.
  • 재회 — 파티 종료 후 서로 다시 만나고 싶은 짝으로 매칭됐을 때.

5.4 상호 선택의 비밀 보장

"다시 만나고 싶은 사람"은 서버에서만 대조합니다. 내가 A를 골랐고 A도 나를 골랐을 때에만 양쪽 레코드가 모두 존재하고, 그때만 매칭 결과에 담깁니다. 한쪽만 고른 경우 어느 쪽 응답에도 그 정보가 실리지 않습니다.
